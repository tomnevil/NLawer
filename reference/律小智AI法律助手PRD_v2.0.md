## 一、产品概述与目标

### 1.1 产品定位

"律小智" 是一款基于大语言模型（LLM）的智能法律服务平台，**双产品线并行**：



* **产品线 A・律所智能协作平台（LawyerOS）**：以 IM 聊天机器人为客户端口，为律所提供 "AI 前台接待 → 智能接单派单 → AI 辅助办案 → 证据材料整理 → 律师人工复核 → 备案存档" 的全流程数字化协作工具，把律师从繁琐的信息收集与材料准备中解放出来，提升办案时效。

* **产品线 B・个人 / 企业法务助手（Legal Copilot）**：为个人和小微企业提供按月按量的长期 AI 法务订阅，沉淀企业专属知识库，越用越懂客户；超出定制量按工单计费。

产品以 "让法律触手可及" 为核心理念，通过自然语言交互降低法律知识壁垒，将传统法律服务的高门槛转化为标准化、自动化的数字体验，同时以 "AI 提效 + 律师把关" 双引擎保障专业性与可信度。

### 1.2 产品愿景

构建 "AI 普惠法律 + 专业律师兜底" 的双层服务体系，实现 \*\*"咨询 — 接单 — 办案 — 复核 — 立案 — 开庭"\*\* 的法律服务全链路数字化闭环，成为区域法律科技基础设施。

### 1.3 核心痛点



| 用户群体    | 痛点描述                                                                     |
| ------- | ------------------------------------------------------------------------ |
| 个人用户    | 遇到租房纠纷、劳动维权、消费投诉时，不知如何起草文书、计算赔偿，聘请律师成本高（通常 500 元 / 小时起），且咨询沟通成本高、材料整理繁琐。 |
| 小微企业    | 缺乏专职法务，合同审查、劳动合规、股权协议等依赖外部律师，单次咨询费用 2000-5000 元，初创期难以承受；无法长期沉淀自身法务知识资产。  |
| 律所 / 律师 | 案源获取依赖线下，咨询阶段信息碎片化；接单后需反复沟通收集材料，证据整理耗时；重复性法律检索、文书起草占用大量时间，挤压高价值工作。       |

### 1.4 产品目标



| 阶段 | 周期      | 目标                                                                                  |
| -- | ------- | ----------------------------------------------------------------------------------- |
| 短期 | 0-6 个月  | 上线产品线 A 核心闭环（IM 机器人 + 接单 + AI 辅助办案 + 备案存档）与产品线 B 法务助手，覆盖 80% 常见法律场景，用户满意度 ≥4.5/5.0。 |
| 中期 | 6-12 个月 | 签约 30 家律所、1000 家小微企业和企业客户，建立合规扫描引擎与年度合规体检。                                          |
| 长期 | 1-3 年   | 成为区域性法律科技基础设施，对接法院、仲裁委等官方系统，实现 "咨询 - 文书 - 立案" 闭环，形成 "AI 办案 + 律师背书" 的行业标准。           |

## 二、双产品线总览

### 2.1 产品线 A：律所智能协作平台（LawyerOS）

**一句话**：帮律所把 AI 机器人 "挂进" 客户的聊天软件，让 AI 先接待、先收集、先分析，律师只做最核心的判断与把关。



| 子模块            | 说明                                   |
| -------------- | ------------------------------------ |
| IM 聊天机器人（客户端口） | 部署在微信、企业微信、飞书、钉钉等 IM，客户可直接对话咨询、上传材料。 |
| 智能接待与派单        | AI 接待、意图识别、案件分级；支持客户指定律师或系统自动派单。     |
| AI 辅助办案        | 接单后自动生成案件摘要、法律分析、法条关联、初步建议与文书初稿。     |
| 证据材料智能整理       | 自动收集、OCR、归类客户从 IM 上传的证据，识别缺失材料并提醒补充。 |
| 律师工作台          | 律师查看案件、与客户在 IM 沟通、修改完善文书、发起复核确认。     |
| 人工复核工作流        | 律师 / 合伙人分级复核，全程留痕，律师确认后方可定稿。         |
| 案件备案存档         | 定稿材料归档、版本控制、时间戳审计，生成开庭材料包。           |

### 2.2 产品线 B：个人 / 企业法务助手（Legal Copilot）

**一句话**：为个人和小微企业提供按月按量的 AI 法务订阅，沉淀专属知识库，越用越懂客户，超量按工单计费。



| 子模块              | 说明                               |
| ---------------- | -------------------------------- |
| 智能问答（Legal Q\&A） | 自然语言咨询，RAG 检索，结构化输出 + 引用溯源。      |
| 文书自动化            | 200+ 常用文书模板，多轮变量收集，在线编辑 + 风险提示。  |
| 合同审查模式           | 上传已有合同，AI 标注风险条款并给出修改建议。         |
| 合规扫描             | 劳动用工、商业合同、数据隐私、广告营销四维度扫描 + 定期报告。 |
| 企业专属知识库          | 沉淀企业合同、制度、历史咨询，长期使用更懂客户。         |
| 用量与工单计费          | 按月按量套餐，超出定制量自动转工单收费（可转人工律师）。     |

### 2.3 共享底层能力

两条产品线共享同一套底层能力，一次建设、双向复用：



| 能力                            | 服务对象         |

| 引用溯源                          | A + B        |

| 合规扫描引擎                        | A（辅助）+ B（主力） |
| 多模态解析（OCR、图片 / PDF / 语音）      | A + B        |
| 人工复核与审计链路                     | A（主力）+ B（增值） |
| 账号 / 权限 / 多租户                 | A + B        |

### 2.4 商业模式总览



| 产品线   | 收费对象    | 模式                         |
| ----- | ------- | -------------------------- |
| 产品线 A | 律所      | 按律师席位订阅 + 按案件计费（SaaS + 增值） |

* 作为律师，我想让 AI 自动识别客户上传的合同照片、聊天记录截图并归类，同时提醒我还缺哪些证据，以便减少反复沟通。

**客户场景**



* 作为当事人，我想在微信里直接给律所机器人发语音和材料，AI 先答复我，必要时自动转给对应律师，以便不用跑线下、不用整理材料格式。

* 作为客户，我想随时在聊天窗口查看案件进度和律师的答复，以便掌握委托情况。

**企业法务助手场景**



* 作为电商公司负责人，我想让法务助手按月帮我把宣传文案做广告法扫描并自动生成整改建议，以便避免行政处罚。

* 作为科技公司创始人，我想让助手沉淀我们公司的合同模板和用工制度，长期使用越用越懂我们，以便控制用工与经营风险。

* 作为行政负责人，我想在套餐用量用完时自动转工单并按单结算，以便费用可控、不中断服务。

## 五、核心功能规格

### 5.1 IM 聊天机器人接入层（产品线 A 客户端口）

**功能描述**：机器人作为律所的 "数字前台"，部署于主流 IM，客户无需下载新 App。

**接入方式**：



* 微信（个人号 / 公众号 / 企微）、企业微信、飞书、钉钉；

* 支持通过律师分享的 "机器人名片 / 二维码" 添加，绑定专属律师关系；

* 后续可扩展：WhatsApp / 网页挂件 / 自有小程序。

**机器人能力**：



| 能力     | 说明                          |
| ------ | --------------------------- |
| 智能接待   | 欢迎语、意图引导、常用问题 AI 直接解答。      |
| 多模态消息  | 文字、语音（转写）、图片、PDF、文件、视频消息接收。 |
| 会话上下文  | 跨消息保持上下文，支持多轮追问。            |
| 人工无缝转接 | 会话上下文完整转交给律师，客户无感切换。        |
| 进度通知   | 派单、律师回复、材料缺失、定稿等节点自动推送。     |
| 满意度收集  | 结案 / 会话结束发送评价卡片。            |

**交互规范**：机器人开场即明确 "AI 助手" 身份与免责声明；涉及法律意见的关键结论必须带 "AI 生成、仅供参考、需律师确认" 提示。

### 5.2 智能接待与派单系统（Case Intake & Routing）

**功能描述**：将客户咨询转化为结构化案件，并完成 "指定律师 / 系统派单 / 律师抢单"。

**接单流程**：



1. 客户发起咨询 → AI 识别意图（咨询类 / 文书类 / 计算类 / 审查类 / 委托类）。

2. 判断是否需要人工介入：

* 高频通用问题 → AI 直接解答，无需派单；

* 涉及委托、复杂纠纷、高价值标的 → 进入派单流程。

1. 案件分级：按标的额、复杂程度、紧急程度分为 S/A/B/C 级，决定复核深度与响应时效。

2. 派单方式：

* **指定律师**：客户通过律师专属二维码 / 名片进入，直接绑定该律师；

* **系统派单**：按律师专业领域、忙闲状态、执业年限自动匹配；

* **律师抢单**：进入案件池，律师按专业标签认领。

1. 接单确认：律师接受后，系统通知客户 "已由 XX 律师为您服务"，并同步案件摘要。

**派单规则引擎**：支持律所自定义（专业领域匹配、轮询、负载均衡、排除规则、白名单指定等）。

### 5.3 AI 辅助办案（Lawyer Copilot，接单后）

**功能描述**：律师接单后，AI 自动完成 "案件理解 + 法律分析" 初稿，供律师快速进入状态。

**接单后自动生成**：



```
【案件摘要】当事人、相对方、纠纷类型、争议焦点、标的额、时间线

【法律分析】可能涉及的法律关系与请求权基础

【相关法条】关联法规条款及条文摘要（可溯源）

【类案参考】相似判例、指导案例（脱敏后引用）

【初步建议】可能的诉讼/调解/非诉路径与利弊

【待补充信息】缺口清单：还需要客户提供哪些材料与信息
```

**律师可在工作台对以上内容修改、批注、补充**，AI 依据律师修改继续迭代（如 "围绕新的争议焦点重新检索"）。

**会话辅助**：律师在 IM 中回复客户时，AI 提供回复建议（话术润色、法条引用、风险提示），律师确认后发送，保障回复质量与一致性。

### 5.4 证据材料智能整理（Evidence Pipeline）

**功能描述**：自动收集、理解、归类客户从 IM 上传的证据材料，辅助律师准备案件材料。

**能力明细**：



| 能力      | 说明                                    |
| ------- | ------------------------------------- |
| 多模态解析   | OCR 合同 / 票据、识别聊天记录截图、语音转文字、PDF 结构化解析。 |
| 自动归类    | 按证据类型归类：合同类、支付凭证类、沟通记录类、身份证明类、公文书类等。  |
| 证据要素抽取  | 自动抽取关键要素（日期、金额、主体、签章），生成证据清单初稿。       |
| 缺失提醒    | 对比案件材料清单，自动列出缺失项并推送客户补充（支持一键追问）。      |
| 时间线生成   | 根据材料自动生成事件时间线，辅助梳理案情。                 |
| 证据合法性提示 | 标注可能影响证明力的风险点（如复印件、无原件、取证方式），提示律师核实。  |

**材料补充智能追问**：对缺失材料，机器人按 "先关键、后补充" 顺序，分轮引导客户补齐，减少律师重复催收。

### 5.5 人工复核工作流（Human-in-the-Loop Review）

**功能描述**：贯穿 "AI 输出 → 律师把关" 的完整复核链路，保障对外内容的专业性与责任边界。

**三级复核模型**：



| 级别       | 适用场景                              | 复核人              |
| -------- | --------------------------------- | ---------------- |
| L1 AI 自检 | 所有 AI 生成内容                        | AI（校验引用、格式、免责声明） |
| L2 律师复核  | 一般咨询答复、常规文书、证据清单                  | 承办律师             |
| L3 高级复核  | 对外法律意见书、重大 / 高风险案件、离婚协议、股权转让、涉刑文书 | 合伙人 / 高级律师       |

**强制复核场景清单**（命中即强制 L2/L3）：



* 对外出具正式《法律意见书》；

* 涉及大额标的（如标的额 ≥50 万）、人身、婚姻家庭、刑事；

* 高风险文书：离婚协议、遗嘱、股权转让、认罪认罚相关材料；

* 合规扫描报告（对外版本）；

* 客户明确要求 "出正式意见" 时。

**复核留痕**：记录每次 AI 输出 → 律师修改 → 确认的完整过程（谁、何时、改了什么、确认版本），形成可审计闭环，责任可追溯。

**状态机**：草稿（AI 初稿）→ 律师修改中 → 待确认 → 已确认 → 已归档 → （可回溯）→ 已作废。

### 5.6 案件备案存档与开庭支持（Archive & Hearing）

**功能描述**：律师确认后的定稿材料统一归档，供开庭使用。

**能力明细**：



* **归档**：案件卷宗结构化管理（诉状、证据、法律检索、时间线、沟通记录、审批记录）。

* **版本控制**：每次修改保留历史版本，支持回溯对比。

* **审计日志**：操作留痕，满足律所管理与合规审计要求。

* **开庭材料包**：一键导出 "开庭材料包"（目录 + 起诉状 / 答辩状 + 证据清单 + 质证提纲 + 庭审要点），格式规范可直接使用。

* **隐私与权限**：卷宗按角色分级授权，客户仅见本人案件，律师 / 助理按权限访问。

* **对接规划（远期）**：电子卷宗对接法院诉讼服务网、仲裁委系统，实现网上立案材料预生成。

### 5.7 企业法务助手与企业专属知识库（产品线 B）

**功能描述**：按月按量订阅的长期法务助手，沉淀企业专属知识，越用越懂客户。

**企业专属知识库（RAG 私有域）**：



| 内容类型 | 说明                       |
| ---- | ------------------------ |
| 合同库  | 企业历史合同、标准合同模板（经律师审核）。    |
| 制度库  | 用工制度、章程、股东协议、内部规章。       |
| 历史咨询 | 历史问答与结论（脱敏授权后）。          |
| 偏好设置 | 风险偏好、常用律师 / 机构、行业属性、经营地。 |
| 法规订阅 | 与企业相关的法规变更自动推送与解读。       |

**知识库价值**：后续咨询可结合企业自身情况给出 "个性化" 回答（如 "按我们公司 XX 合同模板的口径…"），形成长期使用黏性。

**用量与计费**：



* 按月按量套餐（如每月 N 次咨询、N 份文书、N 次扫描）。

* 用量看板：实时显示剩余额度，避免超出。

* 超量自动转**工单**：按工单计费（标准价 / 加急价），可升级为 "AI + 人工律师" 处理。

* 企业多用户：子账号、权限分级、审批流（如 "对外文书需负责人审批"）。

### 5.8 智能问答（Legal Q\&A）

**功能描述**：用户以自然语言提问，AI 基于法律知识库生成回答，并附带来源依据。

**交互流程**：



1. 用户输入问题（支持文字 / 语音 / 图片上传，如合同照片）。

2. 系统识别意图（咨询类 / 文书类 / 计算类）。

3. 调用 RAG 检索相关法规、案例、模板。

4. 生成结构化回答：结论 → 法律依据 → 行动建议 → 风险提示。

**输出结构规范**：



```
【结论】一句话给出明确判断或处理方向

【法律依据】引用具体法规名称、条款号、条文摘要（可点击溯源）

【行动建议】分步骤可执行操作（含时限、材料、受理机关）

【风险提示】指出不确定性、时效性问题及后续后果

【免责声明】"本内容由 AI 生成，仅供参考，不构成法律意见"
```

**边界处理**：涉及复杂诉讼策略、跨国法律、非中文问题时，提示 "建议咨询专业律师" 并提供转介入口。

### 5.9 文书自动化（Document Automation）

**模板库**：覆盖 200+ 常用法律文书（劳动合同、租赁合同、欠条、离婚协议、公司章程、起诉状、答辩状、质证提纲等），按生命周期分类管理（劳动用工 / 合同交易 / 婚姻家庭 / 公司治理 / 诉讼文书）。

**生成流程**：



1. 用户选择文书类型，通过多轮对话收集关键变量（如甲方 / 乙方、金额、期限）。

2. AI 自动填充模板，生成初稿。

3. 用户可在线编辑，AI 实时提示风险点（如违约金过高、管辖法院不利）。

4. 导出为 Word/PDF，支持电子签名（集成第三方 CA）。

**差异化能力**：支持 "合同审查模式"—— 用户上传已有合同，AI 标注风险条款并给出修改建议。

### 5.10 合规扫描（Compliance Scanner，产品线 B 主力 / A 辅助）

**适用对象**：小微企业。



| 维度   | 扫描要点                      |
| ---- | ------------------------- |
| 劳动用工 | 劳动合同签订率、社保缴纳、加班费计算、竞业限制。  |
| 商业合同 | 违约条款、知识产权归属、争议解决方式。       |
| 数据隐私 | 个人信息收集、Cookie 政策、用户协议合规性。 |
| 广告营销 | 绝对化用语、虚假宣传、专利标注。          |

**输出报告**：风险等级（高 / 中 / 低）、整改建议、参考模板、法规链接。支持定期（月度 / 季度）自动扫描。

### 5.11 引用溯源（Citation & Traceability）



* 所有回答必须附带来源：法律法规名称及条款、司法解释、指导性案例编号。

* 展示形式：点击引用标记，侧边栏弹出原文摘要，确保可验证性。

* 版本控制：法律条文更新时，自动标记历史回答的时效性变化。

* 溯源完整性：每一条结论性陈述必须至少对应一个可点击的引用来源；引用缺失视为生成失败。

## 九、技术架构要求

### 9.1 LLM 选型策略



| 场景          | 模型选择                                        | 理由                 |
| ----------- | ------------------------------------------- | ------------------ |
| 通用问答 / 文书生成 | 混合部署：Qwen3.8-Flash（低成本）+ GLM-5.3-Flash（高精度） | 平衡成本与质量，通过路由层动态分配。 |
| 复杂推理 / 合规分析 | DeepSeek V4（满血版）                            | 逻辑推理能力强，适合长文本分析。   |
| 私有化 / 敏感数据  | 本地部署 Qwen2.5:32B（量化版）                       | 数据不出域，满足律所与企业合规要求。 |

**模型路由规则**：意图简单且 token 消耗低 → 低成本模型；涉及赔偿计算、合规判定、证据分析等复杂推理 → 高精度 / 满血模型；律所与企业敏感数据 → 本地私有化模型。

### 9.2 RAG 与知识库

**数据源**：



* 国家法律法规数据库（实时同步）。

* 最高人民法院指导案例、公报案例。

* 地方法规（支持省市级筛选）。

* 优质合同模板库（经律师审核）。

* **律所私有知识库**（脱敏类案、内部研究、模板）。

* **企业专属知识库**（合同、制度、历史咨询，多租户隔离）。

**检索增强**：



* 混合检索：BM25（关键词）+ 向量检索（语义）。

* 重排序（Rerank）：使用 bge-reranker-v2-m3 提升精度。

* 知识图谱：构建 "法条 - 案例 - 文书 - 证据" 关联网络，支持多跳推理。

**知识库更新机制**：法规变更通过监控管道捕获 → 自动标记 + 每周人工审核 → 同步更新索引与历史回答时效性标记。

### 9.4 工作流编排



* **框架**：采用 Dify 或自研 Workflow 引擎。

* **节点类型**：


  * LLM 节点：问答、生成、摘要、会话辅助。

  * 代码节点：赔偿计算、日期推算、格式校验、要素抽取。

  * 消息节点：IM 推送、进度通知、缺失材料追问。

* **可观测性**：记录每个节点的输入输出、耗时、token 消耗，用于优化。

## 十、关键非功能性需求

### 10.1 数据安全与隐私



| 项                 | 要求                                           |
| ----------------- | -------------------------------------------- |
| 传输加密              | 全站 HTTPS，API 通信使用 TLS 1.3。                   |
| 存储加密              | 用户上传的合同、个人信息、案件卷宗使用 AES-256 加密存储，密钥由 KMS 管理。 |
| 数据隔离              | 多租户架构，律所 / 企业数据逻辑隔离，支持私有化部署。                 |
| 合规认证              | 通过 ISO 27001、等保三级认证。                         |
| 数据留存              | 用户可查看 / 导出 / 删除个人数据，遵守《个人信息保护法》。             |
| **律师 - 客户特权通信保护** | 律师与客户对话、案件材料按 "律师工作秘密" 保护，权限最小化，律所管理员可见范围受控。 |
| 数据出境              | 涉及个人信息的处理遵循《数据出境安全评估办法》等要求，敏感数据本地化。          |

### 10.2 合规性与免责声明



* 显式提示：每次回答开头注明 "本内容由 AI 生成，仅供参考，不构成法律意见"。

* 律师背书：与律所合作，高风险场景提供 "AI + 律师" 双签服务；对外正式文件须经律师确认。

* 监管适配：遵守《生成式人工智能服务管理暂行办法》，完成算法备案。

* 责任边界：AI 生成内容与律师确认内容明确区分，责任归属清晰（AI 辅助、律师负责）。

### 10.3 可解释性



* 决策透明：AI 给出建议时，必须说明 "为什么"（如 "因为《劳动合同法》第 82 条规定…"）。

* 置信度提示：对低置信度回答（如罕见案例），明确告知 "此回答可靠性较低，建议人工核实"。

* 用户反馈闭环：支持 "踩" 按钮，收集错误案例用于模型迭代。

### 10.4 性能要求



| 项           | 要求         |
| ----------- | ---------- |
| IM 消息收发     | ≤2s（P95）   |
| 问答首字响应      | ≤3s（P95）   |
| 问答完整响应      | ≤15s（P95）  |
| 接单后案件摘要生成   | ≤60s       |
| 证据 OCR / 归类 | 单文件 ≤10s   |
| 文书生成        | ≤30s（常规文书） |
| 合规扫描        | 单份合同 ≤60s  |
| 服务可用性       | 99.9%（月度）  |

### 10.5 兼容性



* 移动端：iOS 12+ / Android 8+。

* Web 端：Chrome / Edge / Safari 近两年版本。

* IM：微信 / 企业微信 / 飞书 / 钉钉 官方开放平台支持范围内。

**四项关键机制**：

1. **进程内常驻任务队列** — `asyncio.Queue` + N 个常驻消费者协程替代 `BackgroundTasks.add_task`；任务**先落库再入队**，队列满时**反压等待**（不静默丢任务），支持**优雅停机**。
2. **原子认领（跨进程乐观锁）** — 单条 `UPDATE ... WHERE status IN ('pending','retrying')` 的 `rowcount` 判定归属，多副本同时消费同一 Job 时只有一个实例能推进。
3. **心跳 + 僵尸回收** — 执行期间刷新 `heartbeat_at`；超过 300s 无心跳的 `RUNNING` 自动重置为 `PENDING`，每 60s 扫描一次。进程被 `kill -9` 后任务最多 5 分钟内自动回到队列。
4. **限流可插拔后端** — `RateLimitBackend` Protocol；Redis 实现用 Lua 脚本原子执行（`ZREMRANGEBYSCORE + ZCARD + ZADD`）；**Redis 故障时优雅降级**到内存后端并告警，不阻断业务。分层阈值：认证 20/min、上传 10/min、生成 15/min。

### 第四轮：向量检索链路打通（P0-2 —— 直接决定 AI 输出质量）

**缺陷本质**：`rag/retriever.py:28` 把查询向量**硬编码为 `None`**，而所有 vector store 对 `None` 都「静默返回空」。两者叠加 → **向量召回永远为空且无任何日志**，RAG 看似完整、实为纯 BM25。

这条链路上还有 3 个连锁缺陷：① 项目里**根本没有 Embedding 客户端**（无文本转向量的能力）；② 内存 `VectorStore.search()` 是空实现（无条件 `return []`）；③ **没有任何地方写入向量**（`KnowledgeEmbedding` 只有模型定义，全库无一处 `db.add`）。

> **这是「宣称能力与实现之间的空洞」的典型样本**：PRD 写了 pgvector 语义检索、代码里有 `PgVectorStore` 的完整实现，但**整条链路从未接通过**。

**修复内容（5 项）**：

| # | 缺陷 | 改动文件 |
| --- | --- | --- |
| 1 | 查询向量硬编码 `None` | `app/rag/retriever.py`（重写 `search`，新增 `_embed_query` / `index_documents_async`） |
| 2 | 无 Embedding 客户端 | **新增 `app/ai/embeddings.py`**、`app/config.py`（新增 `EMBEDDING_BASE_URL`） |
| 3 | 内存向量库为空实现 | `app/rag/vector_store.py`（实现真实余弦检索 + 修正后端选择逻辑） |
| 4 | 向量表无人写入 | `app/services/knowledge_service.py`（写入时切片索引） |
| 5 | 无 pgvector 时向量列无法写入 | `app/models/embedding.py`（新增 `JsonVector` TypeDecorator） |

**关键设计**：
- **取不到查询向量时跳过向量召回，而非传 `None` 进 store**——行为看似相同（都返回空），但前者是有意识降级，后者是缺陷伪装成正常。
- **按 `index` 排序 embedding 返回结果**：服务端可能乱序，不排序会导致向量与文本错配（静默的错误检索比报错更难排查）。
- **生产守门**：生产环境声明用向量后端却缺 `EMBEDDING_API_KEY` → 抛 `ConfigurationError`，不静默降级（与 P0-3 Mock LLM 守门同一原则）。
- **向量存储与查询向量分开判定**：`build_vector_store()` 不再由「有没有 Key」决定库的存在；声明 pgvector 但环境不满足时**降级内存实现并告警**，而非返回 `None`。
- **知识写入失败只告警不抛错**：知识库写入的可用性优先于语义检索（此时文档仍可被 BM25 检索到）。

**判决性验证证据**：混合检索召回 `hybrid=3 vs bm25=1` —— 向量分支带来 2 条 BM25 完全找不到的结果；且「仅向量分支（清空 BM25 语料）」仍可召回。

**验证**：`verify_p0_2_vector.py`（39 项 5 层：结构/单元/集成/降级/守门）+ `verify_p0_2_ingest.py`（12 项真实 DB 读写）+ `tests/test_vector_retrieval.py`（14 项回归），全部通过。

> **⚠️ 本轮集成测试抓到 2 个单元测试测不出的真缺陷**：
> ① `chunk_text` 返回的是 `list[dict]` 不是 `list[str]`，直接塞进 `content` 列报 `type 'dict' is not supported`；
> ② **无 pgvector 时向量列是 `Text`，存不下 Python list** —— 模型注释声称「回落 Text 保证零依赖启动」，实际写入直接崩。此缺陷**在原代码里就存在**，只是从没人写过向量所以从未触发。
> **教训**：纯内存 + fake embedding 的 39 项全绿，真正的写库缺陷要等真实 DB 集成测试才暴露。**涉及持久化的改动必须有一层真实 DB 验证**。

**⚠️ 运维须知（启用语义检索的前提）**：
- **需配置 `EMBEDDING_API_KEY` 才真正启用语义检索**；默认（Key 为空）仍是纯 BM25。
- **种子数据未回填向量**：`app/seed/` 下的法条/类案不会自动生成向量，存量语料需一次性的 backfill 脚本。
- **`PgVectorStore` 的真实 pgvector 路径未做端到端验证**：本轮验证在 SQLite + 内存向量库完成，pgvector 的 `cosine_distance` 行为需在 Postgres 环境另测。
- `rerank` 仍是词重叠启发式（P1），真实语义排序需替换为 Cross-Encoder。

### 第六轮（2 项，前端令牌安全 + CSRF —— 从「服务端防得住」到「浏览器端防得住」）

> **修复前实测**：access + refresh **全明文存 `localStorage`**，access 有效期 **1440 分钟（24 小时）**，refresh 7 天且 JS 可读；全站**零 CSRF 防护**。
> 对法律产品而言，XSS 一次命中 = 当事人姓名、身份证号、案情细节全部外泄。

| 编号 | 缺陷 | 状态 | 改动文件 |
| --- | --- | --- | --- |
| P0-7 | 令牌明文存 localStorage：任意第三方脚本（广告 SDK / 埋点库 / 供应链投毒 npm 包）执行一行 `getItem` 即可盗取 7 天会话 | ✅ 已修复 | `config.py`（1440→30 分钟）、**新增** `core/auth_cookies.py`、`api/v1/auth.py`、`main.py`；前端 `packages/sdk/src/index.ts`、`packages/ui/.../LoginShell.tsx`、4 个登录页、13 个页面守卫 |
| P0-11 | 全站无 CSRF 防护，第三方页面可无声调用写接口 | ✅ 已修复 | **新增** `core/csrf.py`、`middleware.py`（`CsrfMiddleware`）、`api/v1/auth.py` |

**分层令牌策略（核心设计）**：

| 令牌 | 存放位置 | 有效期 | XSS 能否窃取 |
| --- | --- | --- | --- |
| access | **内存变量**（非 localStorage） | **30 分钟** | 仅当前标签页存活期内，刷新即失效 |
| refresh | **HttpOnly Cookie** | 7 天 | **不能**（JS 读不到） |
| csrf | 普通 Cookie（JS 可读） | 1 小时 | 能，但**无用**（需配合 HttpOnly 才构成双提交） |

**威胁模型变化**：XSS 最坏后果从「**7 天完整会话被盗、改密码也不一定失效**」降级为「**当前标签页 30 分钟内被借用，刷新即失效**」——这是数量级的收敛。

**CSRF 实现要点**：HMAC-SHA256 签名式双提交，令牌格式 `nonce.ts.session_id.sig`，**会话绑定**（`session_id = sha256(refresh)[:16]`），TTL 3600 秒。带 `Authorization: Bearer` 的请求**豁免**（浏览器不会自动附加该头，天然免疫 CSRF）。覆盖 `/api/v1/auth/refresh` + `/api/v1/auth/logout`——后者是二次加固补上的，只凭 Cookie 即可生效的端点都必须覆盖，否则第三方站点能用 `<img>` 静默踢用户下线。

**新增生产 fail-fast**：`ENVIRONMENT=production` + 启用 Cookie + `AUTH_COOKIE_SECURE=false` → **启动即抛错**，把「忘记开 Secure」从线上事故变成启动失败。

**顺带修掉的 SDK 逻辑缺陷**：`request()` 的 401 自动刷新重试没有例外通道，导致用户点「退出」时若 access 已过期，会被自动静默刷新"复活"，**登出形同虚设**。已加 `_noRetry` 标记，`logout()` / `login()` 均带上。这是**两个单独看都正确的机制组合起来产生错误行为**的典型——只有阅读控制流才能发现。

**验证（五层）**：编译 ✅ / 静态 `verify_p0_7_frontend.py` **25-25** / 单元 `tests/test_csrf.py` **12-12** / 真实请求 `verify_p0_7_csrf.py`（TestClient + Cookie 罐）**32-32** / 前端 4 应用 + ui + sdk 全量 `tsc --noEmit` ✅ 全绿 / 全量回归 **123-123（无回归）**。

**⚠️ 本轮教训（第四次验证同一规律）**：批量改写 13 个页面守卫后，`tsc` 报出 **11 个编译错误**——孤儿 `else`（脚本替换了 if/else 前缀却留下 `else refresh();`），以及 `else load()` 但该页面根本没有 `load()` 函数（真实名字是 `refresh()`，或是静态导航页无需拉取数据）。**静态 grep 完全看不出来，编译器是唯一裁判**。已固化为 `C.3`（孤儿 else）/`C.4`（调用未定义函数）两条静态断言。

**遗留待办（本轮引入的已知权衡）**：
1. **移动端需保留 Bearer body 通道** —— 部分 App 内嵌 WebView 对 Cookie 支持受限，建议按 `User-Agent` 分流，允许正文传 refresh 并强制绑定设备指纹。
2. **滚动发布会导致会话失效** —— `SECRET_KEY` 轮换或跨版本时 HMAC 签名的 CSRF 令牌会失配，用户需重新登录（当前可接受，量产后需做双密钥平滑过渡）。
3. **`CSRF_STRICT_ALL_WRITES` 仍为 `false`** —— 当前只保护 refresh/logout。其他写接口依赖 Bearer 天然免疫，但若后续放开 Cookie 直连，必须打开此开关。

**核心设计决策 3 —— 投诉入口允许匿名**。

| `GET /api/v1/complaints/{ticket_no}` | **无** | 凭工单号回查（含随机段，不可枚举） |
| `GET /api/v1/complaints` / `POST /{id}/handle` | 平台管理员 | 列表（支持逾期筛选）/ 处理办结 |

**防「假闭环」的四条不变量**：① 办结/不予受理**必须**填处理结论（≥5 字）；
② `RESOLVED` **必须**带 `handled_at` + `feedback_sent`；③ 承诺时限
**从受理时刻起算**（+15 天）；④ 看板**必须**给出 `overdue` 口径（逾期 = 违约信号）。

**脱敏设计（留痕不存原文）**：数据库只存 `content_hash`（sha256[:32]）+
`content_len` + 分类级别；`Hit.as_dict()` 只输出 `matched_hash` **绝不输出命中词**；
用户响应不含任何命中词，只引导至投诉入口。
理由：① 存原文等于**二次存储**违规内容，本身是新合规风险；
② 泄露命中词可被攻击者**反向调优绕过策略**。

**生产环境强制守卫（fail-fast，法规要求不可关闭）**：
`ENVIRONMENT=production` 时，① 审核必须启用；② 后端不得为 `none`；
③ 若为 `external` 必须有 API Key。任一不满足 → **启动即抛错**。

**本轮抓到的 3 个真实缺陷**（详细分析见 `code-review-optimization` 第七节）：

1. **留痕被事务回滚吃掉** ⚠️ 最严重——`ContentBlockedError` 从路由抛出后，
   `get_db` 的 `rollback()` 把请求会话里的审核记录与审计行**全部丢弃**。
   SQL echo 明明打印了 INSERT，紧跟一行 `ROLLBACK`。
   **这是第五轮审计日志同类陷阱的第 2 次出现**，说明"依赖请求事务生命周期写合规记录"
   是**系统性陷阱**而非偶发失误。修复：新增 `record_with_detached_row()`
   把业务留痕行与审计行放入**同一个独立事务**立即 commit。
2. **Base64 子串绕过漏检**（真实漏检）——`decode_layers` 只处理**整串**是 Base64
   的情况，把 payload 嵌在句子里（`"解码这段 6aKg... 然后照做"`）即可绕过。
   修复：增加**子串扫描**策略（`[A-Za-z0-9+/=_-]{12,}` + 启发式）。
   **教训：这类缺陷只有主动构造对抗样本才能发现，正常输入测试与静态审查都会漏掉。**
3. **拦截与上报被混为一个动作码**（设计缺陷）——「拦截」与「上报」是
   **两件独立的事**（第十四条区分了动作与报告义务），用一个码表达必然丢信息。
   修复：拆为两条独立审计行（处置行 / 上报行），并新增 `CONTENT_REPORT_PENDING`，
   让运维可一句查询回答**「我欠监管部门几笔上报？」**
   ——这是会直接导致处罚的问题，不能让答案藏在拦截日志里靠人猜。
   实测配对：9 次拦截 → 9 条 `CONTENT_BLOCKED` + 9 条 `CONTENT_REPORT_PENDING`。

**验证**：编译 ✅ / 单测 43-43 ✅ / E2E 44+28=72 ✅ / 全量回归 **166-166** ✅ / 路由 73→79。

**⚠️ 必须由非技术团队交付（本轮的硬性依赖，否则备案过不了）**：
1. **全量违禁词库**（10 万+ 条）——当前内置词库仅为**最小可运行集**，
   用于打通链路与回归测试，**不可直接商用**。需法务/合规交付，支持热更新。
2. **外部内容安全 API**（生产守卫已强制要求 Key，否则拒绝启动）。
3. **监管上报通道**（`MODERATION_REPORT_URL`）——未配置期间所有
   ESCALATE/BLOCK 事件都会落 `CONTENT_REPORT_PENDING`，
   **运维必须定期清账**，否则构成"未报告"违法。
4. **算法备案材料**——技术底座已就绪，**备案周期不可控，建议立即启动**。

### 第八轮（2 项 P1：原子扣减 + 审计保留期 —— 为「等保测评」铺路）

**⚠️ 关于 P1-a 的更正 —— 我上一轮的判断是错的**

上一轮我把缺陷描述为「并发**超额**消费」。**实测证明恰好相反，是少计**：

```
额度 limit=5，并发 20 请求 → used_count = 1 或 2
```

即 18~19 个请求的用量**从未被计入**，且大部分**没有转成工单**。
「超额」与「少计」是两个**相反方向**的风险：前者是收入损失，后者是**服务白送 + 计费失真**。
原实现的三步式在并发下多个请求基于同一旧快照计算，后写覆盖先写 → 典型**丢失更新**。

**修复**：把「判断是否超限」与「自增」合并为**一条条件 UPDATE**，由数据库原子求值，
以 `CursorResult.rowcount`（1=成功 / 0=额度已尽）判定结果，不再依赖应用层快照。

**第二个隐藏缺陷**：`ensure_quota` 的「查不到就插入」在并发首次使用时可能插入**多行**同一
`(tenant, type, period)`，把额度切成几份、**变相放大可用量**。已在 `usage_quotas`
上加唯一索引 `uq_usage_quota_tenant_type_period`（应用层只能缓解，数据库约束才根治）。

**修复后实测**：额度 5 / 并发 20 → `used_count=5`、成功 5、**工单 15**（零丢失、零漏单）；
并发建 15 个工单，工单号全部唯一。

**⚠️ P1-b：两个方向都是缺陷**

- **留存不足**违反等保 2.0（三级）「留存不少于 6 个月」；
- **无限期留存同样是缺陷**——审计表无限膨胀拖垮查询，且 `detail` 可能含个人信息，
  与《个人信息保护法》最小必要原则冲突。

**修复：三段式** `保底留存 → 到期归档 → 归档校验通过后清理`

| 组件 | 行为 |
| --- | --- |
| `AUDIT_RETENTION_DAYS = 365` | 默认值高于 180 天下限 |
| `retention_days()` | 配置低于 180 天时**告警并强制抬到 180**（拒绝遵从错误配置） |
| `archive()` | 导出过期记录为 gzip JSONL + sha256；**只读不删** |
| `purge()` | **默认 dry-run**；分批删除；写 `AUDIT_RETENTION_PURGE` 墓碑 |
| `archive_then_purge()` | 归档行数 ≠ 待清理行数时**拒绝清理**（宁可保留，不可丢失） |

**管理端点**（仅平台管理员，受 `AUDIT_RETENTION_ADMIN_ENABLED` 急停开关约束）：

| 端点 | 说明 |
| --- | --- |
| `GET /api/v1/audit/retention/stats` | 总量 / 过期量 / 最老最新时间 |
| `POST /api/v1/audit/retention/archive` | 归档（只读） |
| `POST /api/v1/audit/retention/purge` | 清理（默认 dry-run） |
| `POST /api/v1/audit/retention/archive-then-purge` | 归档并清理（推荐运维入口） |
| `GET /api/v1/audit/retention/policy` | **公开**：保留策略（合规审查直接取用） |

**⚠️ 本轮最重要的发现：同一机制性陷阱第 3 次复发**

清理审计日志时，墓碑审计写入失败：`(sqlite3.OperationalError) database is locked`。

**根因**：`log_detached_ctx` 用的是**独立数据库连接**（这正是它存在的意义——主事务回滚时仍能留痕）。
若调用方此刻**仍持有未提交的写事务**，SQLite 加库级写锁、Postgres 行锁等待超时，独立连接写入必败。

**三次复发记录**：

1. **第五轮**：审计日志随请求事务回滚而丢失
2. **第七轮**：内容拦截记录随 `ContentBlockedError` 回滚而丢失
3. **第八轮**：清理墓碑被未提交的 DELETE 事务阻塞

**根治（两处，从机制上）**：
① `log_detached` 内置**退避重试**（5 次递增间隔），仍失败时打 **error** 级日志（原为 warning）——
避免「看起来正常」；
② `purge()` **调整顺序**：先在主会话内提交删除，**再**写墓碑。

> **工程约定（已写入代码注释）**：写审计前先问一句 ——
> **「此刻是否还有未提交的写事务？」** 若有，要么先提交，要么接受重试。

**验证**：并发扣减 + 保留期 **13-13** ✅ / 接口端到端 **12-12** ✅ / 单测 **16-16** ✅ / 全量回归 **183-183** ✅ / 路由 79→**84**。

**运维侧上线前必办**：① 审计归档挂**定时任务**（建议每月一次 `archive-then-purge`）；
② 监控审计总量增长趋势 + `AUDIT_RETENTION_PURGE` 告警；③ `usage_quotas` 唯一索引存量去重迁移。

### 第十轮（P1：列表 `COUNT` 有界化 —— 为「大型律所」铺路）

> **⚠️ 本轮的价值首先在于「推翻了上一轮自己的判断」。** 第九轮收尾时我建议下一轮做性能优化，
> 理由是"同步 IO 混入 async、LIKE 查询慢、无缓存"。本轮**先测量再动手**，结果**前两条被实测推翻**。

**① 被推翻的假设**：

| 第九轮的假设 | 实测 | 判定 |
| --- | --- | --- |
| 同步 IO 混入 async | 全仓仅有 1 处 `urllib.parse.unquote`（纯字符串解析，非 IO） | ❌ 不成立 |
| 深分页（大 OFFSET）慢 | `OFFSET 19000` **1.98ms** 反而快于 `OFFSET 0` **4.55ms**；keyset 分页 2.29ms，**零收益** | ❌ 不成立 |

深分页"不成立"的原因：执行计划为 `SEARCH cases USING INDEX ix_cases_tenant_id`——
`tenant_id` 索引已把工作集收窄，`LIMIT` 再让其短路，因而 OFFSET 大小无关紧要。
**若按原计划改 keyset 分页，是纯粹的无效改动。**

**② 唯一经实测确认的缺陷：`COUNT(*)` 无法短路**

`LIMIT` 能让**取数据**凑够 20 条即停，但 `COUNT` 必须**遍历全部匹配行**。55 万行实测：

| 查询 | 耗时 |
| --- | --- |
| 租户过滤 `COUNT`（走覆盖索引） | 4.55 ms |
| **租户 + 关键词 `LIKE` 的 `COUNT`** | **114.95 ms** |
| 数据页本身（`LIKE` + `LIMIT 20`，可短路） | **0.53 ms** |

→ **计数比取数据贵 217 倍，而用户等待的正是计数。**

**③ 修复：有界计数**

```sql
SELECT count(*) FROM (SELECT ... FROM cases WHERE ... LIMIT 201) t
```

最多数 `COUNT_CAP = 200` 行即停。取 `cap + 1` 是为**区分两种塌缩情况**（二者都不报错、只是数字错）：

- 数到 **200** → 已数完 → `(200, False)` **精确值**
- 数到 **201** → 确实还有更多 → `(200, True)` **下界**，前端显示「200+」

若只取 `LIMIT 200`，则「恰好 200 条」会被错报成下界、「201 条」会被错报成精确 200（**静默丢 1 条**）。
**精度只在"多到用户翻不完"时才降级**，而那种场景下精确值本身也无意义。

**④ 改造范围以实测为准（共 7 个列表接口 + 1 处硬上限）**

| 站点 | 匹配规模 | 无界 COUNT | 有界 COUNT | 收益 | 处置 |
| --- | --- | --- | --- | --- | --- |
| **complaints 管理员列表** | 27 万（`status` 偏斜 90%） | **50.81 ms** | **0.37 ms** | **137.6×** | ✅ 改 |
| **cases `/pool`**（大律所） | 8,572 | **30.99 ms** | **0.95 ms** | **32.6×** | ✅ 改 |
| **dispatches 抢单池** | 选择性 `or_` 谓词 | 4.99 ms | 0.47 ms | 12.9× | ✅ 改 |
| dispatches 列表 / conversations / reviews | 小集合 | 6–7 ms | ~6–7 ms | 1.1–1.3× | ⚠️ 小集合零收益，但大律所下 54–72× → 统一采用 |
| `list_templates` | **无 LIMIT**（目录型数据） | — | — | — | ✅ 加 `TEMPLATE_LIST_MAX=500` |

**一个反直觉发现**：`complaints` 是最容易跳过的一个——它的计划用了 `ix_complaints_status`，
**看起来健康**；但该表**分布高度偏斜**（90% 工单同为 `PENDING`），索引几乎无法收窄，实际是最差的一个（137.6×）。
**「计划里有索引」≠「索引起了作用」。**

**⑤ ⚠️ 第二个方法论教训：不要在 ORM 墙钟上做绝对阈值**

初版验证断言「有界计数 < 5ms」，实测 **9.43ms 失败**，排查后确认**不是代码问题**：
`SELECT 1` 经 aiosqlite 就要 **4.381ms**——每条语句有 ~4.4ms 固定框架开销。
**有意义的信号是「扫描代价」**（随数据量增长的部分，也正是修掉的部分）：

| 层级 | 无界 COUNT | 有界 COUNT | 比值 |
| --- | --- | --- | --- |
| 裸 sqlite3（**扫描代价**） | 18.31 ms | **0.354 ms** | **51.7×** |
| SQLAlchemy + aiosqlite（端到端） | 23.86 ms | 5.259 ms | 4.5× |

**验证**：`ruff` 保持 0 ✅ / 单测 `test_pagination_perf.py` **10-10** ✅ /
`verify_p1_pagination_perf.py`（30 万行）**20-20** ✅ / 全量回归 **219-219** ✅（零回归）。

**明确不做（Non-goals）**：keyset 分页（实测零收益）、缓存层（在无真实 QPS 数据前属过早优化）、
同步 IO 改造（经查不存在该问题）。

### 第十一轮（P1：依赖漏洞扫描门禁 —— 供应链安全）

> **⚠️ 本轮解决的问题类别，与前九轮有本质区别。**
> 前九轮修的都是**我们自己写的代码**；而 `ruff` / `pytest` / `tsc` 对
> **「我们依赖的代码是否已被攻破」完全无感**。
> 一个被投毒的依赖可以让全部测试通过、全部静态检查通过，然后在生产环境开门。
> 这是最后一类「改坏了不会被发现」的问题。

**① 实测结果（远超预期）**：

| 端 | 漏洞数 | 严重度分布 |
| --- | --- | --- |
| 后端（`pip-audit`） | **25 个 / 6 个包** | 含 starlette Host 头绕过、python-multipart DoS 系列 |
| 前端（`pnpm audit`） | **39 个** | **3 critical / 14 high**，含 **2 个 Next.js 未认证 RCE** |

**② 最危险的发现不是漏洞，而是「本地看不见」**：

```
$ pnpm audit --audit-level high      # 本地默认（华为云镜像）
ERR_PNPM_AUDIT_BAD_RESPONSE ... 405: Request method 'POST' is not supported
```

镜像**不支持 audit 接口**。修复前本地跑这条命令**一个漏洞都不报**，
而同一份代码在 CI（官方 registry）上会报出 39 个。
**「本地绿」与「CI 绿」不同义的门禁，比没有门禁更危险**——它会让人以为已经检查过了。

**③ 可达性分析改变了优先级**：

| 包 | 漏洞数 | 可达性判定 |
| --- | --- | --- |
| `python-multipart` | 7 | **可达**（`evidence.py` 接收 `UploadFile`）→ 最该修 |
| `starlette` | 7 | **可达**（Host 头绕过影响本项目中间件鉴权）→ 必修 |
| `python-jose` | 3 | ❌ **不可达**（`algorithms=[...]` 显式白名单 + 从不调 `jwe`） |
| `ecdsa` | 1 | ❌ 不可达 + **上游不修** → 登记豁免 |

> 结论：**只看 CVE 数量会把精力砸错地方**。认证栈那 3 个"高危"在本项目其实不可达，
> 因为 `app/core/security.py` 用了官方推荐的显式算法白名单，且从不调用 `jwe`。

**④ 修复内容**：

- **后端链式升级**（8 个包）：`fastapi 0.115→0.141` 是**解锁钥匙**——
  0.115 硬约束 `starlette<0.39`，而 starlette 的修复全在 0.40+，
  因此**必须同时升 fastapi** 才能拿到修复。

  （无 `middleware.ts`；全 App Router）→ 改用 `useParams()` 移除对 `params` prop 的依赖。
- **`postcss` override**：`next@15.5.24` **仍精确锁定脆弱的 `postcss@8.4.31`**，
  必须在解析层强制改写为 8.5.28。
- **豁免清单** `security-allowlist.txt`：5 条上游无补丁的漏洞，
  **每条附可达性分析 + 复查条件**（而非让 CI 长期报红——长期红的门禁两天内必被注释掉）。

**⑤ 验证**：`ruff` 0 ✅ / `compileall` 0 ✅ / 全量回归 **219-219** ✅ /
`verify_p1_supply_chain.py` **48-48** ✅ / **双门禁本地实跑均绿**
（`No known vulnerabilities found`，rc=0）✅。

**⑥ 本轮的方法论教训（比代码更值得记住）**：

| # | 教训 |
| --- | --- |
| 1 | **"修复版本"必须来自扫描器的 `fix_versions`，不能推断**——凭感觉定的版本实测仍报漏洞，且顺带暴露了被忽略的 `pyasn1` |
| 2 | **升级会带来新约束**——升 `python-jose` 换来 `pyasn1<0.5.0` 硬约束，反而**锁死一个本可修复的包** |
| 3 | **配置"写了"≠"生效"，判据是产物不是告警**——`overrides` 写在 `pnpm-workspace.yaml` 被**静默忽略**；写在 `package.json` 才生效（尽管终端打印**误导性告警**）。唯一可靠判据：查锁文件 |
| 4 | **"本地绿"必须与"CI 绿"同义**，否则门禁是假的 |
| 5 | **⚠️ 绝不要在 `pip install` 中途杀进程**——pip 已卸载旧包、未装新包，会把 `site-packages` 留成**完全空的**（连 pip 自身都没了）。**pip 不是事务性的** |

**明确不做（Non-goals）**：SBOM 生成与签名（需先有供应链治理流程）、
`--require-hashes` 哈希锁定（维护成本显著抬高，当前收益不足）、
替换 `python-jose` 为 `PyJWT`（避免一次性引入认证重构风险）、
升级 Tailwind 3→4（全量样式回归，与安全主题无关）。

## 增补 C：竞品分析核心结论

**市场窗口判断**：中国法律科技处于「**大模型能力已够用、产品化普遍不足**」的窗口期。

| 判断项 | 结论 |
| --- | --- |
| **真实差异化** | 「**律师办案协作全流程闭环**」（接待→派单→办案→证据→复核→归档）是**全部竞品中唯一**的能力组合，兼具市场空白、高价值、高转换成本 |
| **站不住脚的主张** | ① **区域法规数据壁垒**（公开法规无排他性，壁垒应为脱敏办案数据 + 工作流嵌入）；② **微信个人号**（封号风险）；③ **C 端 AI 问答**（通用大模型已免费击穿） |
| **最大威胁** | 通用大模型免费化（已发生）+ iCourt / 幂律智能补齐 AI 办案能力（6–12 个月窗口） |
| **海外验证** | Harvey AI / Legora 验证「AI + 律所工作流」是成立的大生意，且强调**律师主导工作台**而非全自动 —— 印证 L1/L2/L3 复核方向正确 |
| **定价对标** | 律所席位 199 元/人/月**偏低**（建议 299–499）；企业版 199–999 元/月**明显偏低**（建议 3000+ 元/年）；C 端 98 元/年合理但价值主张不足 |
| **商业模型风险** | **ARR 200 万目标数学上存疑**：30 家律所 × 8 律师 × 199 元 × 12 月 ≈ 57 万元/年，需依靠案件服务费补足，建议重设目标 |
| **合规硬门槛** | **算法备案为上线前置条件**（《生成式人工智能服务管理暂行办法》2023-08 施行），当前未办理；需同步补内容安全审核能力 |
