§0 结论摘要（TL;DR）
───────────────────────────────────────────────────────────────────────────────
1. **技术障碍比预期小得多**：`cdp.py` 的**唯一**平台绑定是 `CHROME_CANDIDATES`
   （5 行 Windows 路径）；启动参数（`--headless=new` / `--no-sandbox` / `creationflags=0`）
   本就跨平台。**全仓库其余 `verify_*.py` 零平台绑定**（已全扫）。
2. **成本比预期低得多**：GitHub `ubuntu-latest`（Ubuntu 24.04）**预装**
   Chrome 152 / Chromium 152 / Edge 152 / Firefox 155 **以及 Node.js 22.23.2**
   ⇒ 浏览器 job **零安装成本**（不需要 `apt-get`、不需要 playwright 下载）。
3. 🚨 **摸底过程中揪出一个「从不执行」的新实例（比原议题更急）**：
   `verify_typography.py`（`GATED_STATIC`，棘轮冻结 0/0）在 CI 里 **exit 2**
   ⇒ `run_ci_probes.py` 阶段 3 记「⏭ SKIP(环境)」⇒ **棘轮从未被评估**。
   本窗口刚落地的 T2b / T2c **在 CI 里一条都没跑**。**已实测坐实**（§2）。
4. 🚨 **且降级态会产假阳**：merge 不可用时探针退化成「字面量拼接」，
   会把**两个互斥的字号类**当成共存 ⇒ 实测报出 1 条**假缺陷**（`DataTable.tsx:628`）。
   ⇒ 「让它在 CI 里跑」必须**真的接上 merge**，**不能**靠「降级也判」。
5. **建议分 4 期**：Phase 0（零新增 job，补上 §3 的缺口）→ Phase 1（极低成本的
   「仪器自检」job）→ Phase 2（单端）→ Phase 3（四端+种子库）。
   ⚠️ **Phase 3 有硬前置**：`verify_adjacent_targets.py` 现在**实测 exit 1（真缺陷 4 对）**，
   直接接进去第一天就是红的（项目教训：长期红的门禁两天内必被注释掉）。

§2 🚨 新发现 A：`verify_typography.py` 在 CI 里**从不被评估**（已实测坐实）
───────────────────────────────────────────────────────────────────────────────
2.1 机制（读码 + 实测两遍）
    `verify_typography.py:304-306`（`twmerge_blocks` 守卫）：
        node = _node_bin()
        if not node or not (FRONTEND / "node_modules" / "tailwind-merge").exists():
            return None
    CI 里：`node` **有**（runner 预装，§1.3）—— **卡住的是 `frontend/node_modules`**
    （`evidence` job 从不 `pnpm install`，§1.2）。
    ⇒ `twmerge_blocks()` 返回 `None` ⇒ T2c 落进 `env` 列表（`:967-969`）
    ⇒ `summary_exit()`（`:873-874`）**先判 `env_broken`** ⇒ 返回 **2**
    ⇒ `run_ci_probes.py:868-870` 把 `rc == 2` 记为「⏭ SKIP(环境)」**并跳过棘轮判定**。
    ⇒ **`verify_typography.py` 的棘轮（冻结 0/0）在 CI 里从未被评估。**

2.2 实测（模拟 CI：**只**摘 `frontend/node_modules`，源码树原封不动）
    做法：代理对象包住真实 `FRONTEND`，仅 `FRONTEND / "node_modules"` 指向不存在，
    其余透传 ⇒ **唯一变量**就是 node_modules 的有无。**独立进程**各跑一次。
    ┌──────────────────────────────────────────────────────────────────┐
    │ 状态            判对数  缺陷  env   summary_exit                 │
    │ 本机真实（A）      6     0    0     0                            │
    │ 模拟 CI（B）       8     1    1     2   ← CI 的实际状态          │
    └──────────────────────────────────────────────────────────────────┘
    ⚠️ **第一版实验是错的、已废弃**：它把整个 `FRONTEND` 换成空临时目录 ⇒
       **源码扫描也空了**（输出「扫描：0 个 `className` 块」+ 多出一条 T4 env）
       ⇒ exit 2 的成因被污染。**变量没控住**，结论不成立。修正版（上表）才作数。

2.3 🚨 发现 B：降级态会产**假阳**（同一实验暴露）
    模拟 CI 里报出的唯一缺陷：
        [T2] 正文档 `text-body-sm` 被 `leading-5` 压到 **1.538** < 1.65
             —— frontend/packages/ui/src/components/DataTable.tsx:628
    读源码（`DataTable.tsx:626-630`）：
        className={cn(
          "truncate text-body-sm text-ink-800",
          col.numeric && "num text-[11px] leading-5"
        )}
    **两个块里的字号类互斥**：`col.numeric` 为真时字号是 `text-[11px]`，不是 `text-body-sm`。
    merge 实测（node 直跑 `tailwind-merge`，库默认与项目配置**同结果**）：
        in : "truncate text-body-sm text-ink-800" + "num text-[11px] leading-5"
        out: "truncate text-ink-800 num text-[11px] leading-5"   ← text-body-sm 被吞
    ⇒ 真实行为下 `leading-5`(1.538) 作用在 **11px**（caption 档，非正文）⇒ **合法**。
    ⇒ **CI 降级态那条是假阳**：它把两个互斥块按字面量拼接，误判成 `text-body-sm` 与
      `leading-5` 共存。**探针自己在 `:957` 已声明这种降级是「保守」的**，
      但「保守」的代价在这里表现为**假红**。
    ⇒ **推论（对本议题关键）**：把 typography 接进 CI，**必须让它拿到
      `frontend/node_modules`**（真 merge），**不能**「反正降级也判」。

2.4 🚨 **发现 C（结构性根因）：阶段 3 的「跳过」永远不会被判红**
    实测 `run_ci_probes.py` 里 `r_skipped` **只出现 3 次**：初始化（`:860`）·
    追加（`:869`）· 汇总打印（`:893`）。**它不参与任何失败判定。**
    阶段 3 之后的所有失败判据只有三条：`if failed` · `if skipped and not passed`
    （**注意：`skipped` 是阶段 2 的列表，不含阶段 3**）· `if r_failed`。
    ⇒ 阶段 3 的探针**可以永久 SKIP 而门禁照绿**。
    ⚠️ 这与项目既有纪律**不一致**：坑 50 明确要求「棘轮『取不到条数』**必须判红**」——
       但那是**脚本内部**的防线；`rc == 2` 在**运行器层面、判定之前**就被划进 SKIP，
       **连坑 50 那条防线都不会被触发**。
    ⚠️ 阶段 2 的跳过有「全部跳过且无一通过 ⇒ 判红」（`:909`）兜底，**阶段 3 没有对应物**。
    ⇒ 这正是 §2.1 那条静默能长期存在的原因：**没有任何机制会发现它**。
    ⇒ **建议**：Phase 0 修好之后，补一条守卫 ——「阶段 3 出现 SKIP ⇒ 判红，除非该探针
      在名册里**显式登记了豁免理由**」。**顺序不能反**（先修，再加守卫，否则 CI 立刻红）。

§3 分级方案（每期：改动点 / 成本 / 收益 / 风险）
───────────────────────────────────────────────────────────────────────────────

■ Phase 0 —— 补上 §2 的「从不执行」缺口（**零新增 job**，成本最低）
  目标：让 T2 / T2b / T2c **真的在 CI 里执行**。
  两条路线（**需拍板选一**）：
    0-A【推荐】`frontend` job 里加一步。该 job **已有** node + `node_modules`（`pnpm
        install --frozen-lockfile`）。改动：
          · 加 `pip install websockets==13.1`（`verify_typography.py:123`
            有 `from cdp import Browser` ⇒ 需要 `websockets`；该 job 目前不装 Python 依赖）
          · 加一步 `python3 ../evidence/verify_typography.py --source-only`，断言 exit 0
        ⚠️ 连带：`run_ci_probes.py` 的棘轮在 `evidence` job 里仍会对它 SKIP
           ⇒ 必须在名册里**表态**（把它从 `GATED_STATIC` 挪到 `CI_ELSEWHERE` 一类），
           否则出现「名册说棘轮在管、实际两个 job 都不判」的**假接线**。
    0-B【更统一、更贵】给 `evidence` job 加 `setup-node` + `pnpm install`。
        好处：棘轮逻辑一行不改、T2/T2b/T2c 与其它 `GATED_STATIC` 走同一路径。
        代价：多一次依赖安装（有 pnpm 缓存后约 40–60s）。
  ⇒ **建议 0-B**：改动面最小（不动棘轮语义），且避免「同一判据在两个 job 里各有一套期望值」。
  0-2【**必须后置**】补 §2.4 那条守卫：「阶段 3 出现 SKIP ⇒ 判红，除非名册里显式登记豁免」。
      ⚠️ **顺序不能反** —— 先修 0-A/0-B，再加守卫；否则 CI 立刻变红（正是 §2.1 的现状）。

■ Phase 1 —— 新增「仪器自检」job（**极低成本**，解锁 §1.9 那 4 条）
  改动：`evidence/cdp.py:26-32` 补 Linux 候选 + `CHROME_BIN` 覆盖；
       新增 job `browser-selftest`：Checkout → Setup Python 3.12 → `pip install -r
       backend/requirements.txt` → 跑 4 条 `--self-test`。
  成本：**无浏览器安装**（预装）；4 条自检 ≈38s + 依赖安装。
  收益：① 证明「CDP 仪器在 Linux 上没坏」（这正是 `--self-test` 的用途）；
        ② `SELFTEST_ENV_BOUND` 从 **10 → 6**；③ 为 Phase 2 先趟平路径/环境问题。
  风险：低。唯一未知是 headless Chrome 152 在 Linux 上的行为（§5）。

■ Phase 2 —— 「browser」job（单端，中成本）
  覆盖 §1.8 的 B/C 级（8 条）：dark_mode · reduced_motion · breakpoints ·
  im_safe_area · im_tabs · mobile_actionbar · im_e2e · admin_413_toast_e2e。
  设计要点：
    · 用 **`pnpm build` + `pnpm start`（生产模式）**，**不用 `next dev`**
      —— dev 的按需编译是 flaky 主源，且本项目本机已踩过「一个回合只能起 1 个 dev」。
    · 后端用 `uvicorn` + `DATABASE_URL=sqlite+aiosqlite`（照抄 `evidence` job 的 env 块）。
    · 起服务后**必须等健康检查**（轮询 `/healthz` 之类）再跑探针，不能 `sleep` 赌。
  成本：估 4 端构建中的 1–2 端 + 后端；分钟级。
  风险：中。冷启动超时、端口冲突、探针自身的等待参数需按 CI 机器速度调。

■ Phase 3 —— 四端 + 种子库（最重）
  覆盖 D/E/F/G 级（8 条）：mobile_375 · mobile_safe_area · tap_targets ·
  adjacent_targets · render_e2e · runtime_health · task_center_e2e ·
  contract_review_gate_e2e。
  🚨 **硬前置**：`verify_adjacent_targets.py` **已知 exit 1**（出处：该脚本在
     `run_ci_probes.py` 的 `NOT_GATED` 登记注释，**2026-09-21 实测** —— A1 报 4 对相邻
     可点元素 `gap=4px < 8px`，全部出自 1 条根因，落在 `lawyer/archives` 与
     `lawyer/dispatches` 两页的 `.num` 分页按钮上。**本次未复跑**，按登记值引用）。
    直接接进 CI ⇒ **第一天就是红的**。必须先「修缺陷」或「先用棘轮放行已知欠账」。
  成本：4 端构建 + 后端 + 种子数据 + 26 页 × 多账号 ⇒ 每 PR **10–15 min** 量级。
  ⇒ **强烈建议只在 `main` / 夜间 / 手动 `workflow_dispatch` 触发**，不进 PR 必跑路径。

■ 11.7 修 `verify_task_center_e2e` 的 rc=2（2026-09-25 · 与裁定**无关**，先修掉）

  ✅ **结果：rc=2 → rc=0（8/8 通过）**。W1–W4（web 抽屉）+ L1/L2（律师端 /jobs）
     + A1/A2（管理端 /jobs）全绿；`W4 clicked=clicked, gone=no-btn`。

  🚨 **两层根因（修了第一层才看见第二层）**：

  ① **探针自己猜库路径** ⇒ 编排器的隔离库静默失效。
     它自带一个 `resolve_live_db()` 按硬编码候选路径（`storage/nlawer.db`、
     `backend/demo_8001.db` …）挑「jobs 最多」的那张；而编排器是用 `DATABASE_URL`
     把后端指向**隔离临时库**的 ⇒ 探针把种子写进了**另一张库**、后端读不到。
     ⇒ 与**坑 64**「检查集合也必须读真源」同族：**「谁是运行库」只有后端的启动环境说了算**。
     修法：抽成 `evidence/envprobe.resolve_live_db()` —— **先读 `DATABASE_URL_SYNC` /
     `DATABASE_URL`，猜路径只作兜底**；`verify_ws_msg_type_bypass.py` 同一处硬编码
     （`DB = BACKEND_DIR / "demo_8001.db"`）一并改掉。

     ⚠️ **后者更险**：它读回空列表 ⇒ 会把「**产品有洞（rc=1）**」误报成
     「**环境问题（rc=2）**」。它此前 rc=0 是因为产品**已加固**，**不是因为测对了**。

  ② **`seed_demo.py --reset` 根本不建 `jobs`** ⇒ 「复制已有行当模板」在干净库上必然失败。
     实测：隔离库 `SELECT COUNT(*) FROM jobs` = **0**；旧硬编码目标 `demo_8001.db` 也是 0
     （真正有 jobs 的是 `backend/storage/nlawer.db`，13 条）。
     ⇒ 本机旧数据**长期掩盖**了这个假设（坑 69 形状）。
     修法：加第二条路径 `_create_failed_via_service()` —— 走**产品自己的建行路径**
     （`JobService.enqueue` + `Job` 模型 + `async_session_factory`），**不手搓 SQL**。
     ⚠️ 因为 `Enum(native_enum=False)` 存的是**枚举名**（真实行是 `'COMPLETED'`），
     而 `.value` 是 `'completed'` ⇒ 手搓 INSERT 会**静默写错域** ⇒ `GET /jobs` 整条 500
     ⇒ 抽屉「暂无任务」。**能调产品的服务就不要手搓 SQL。**

  ③ **顺带降噪**：`settings.DEBUG` 默认 `True`，而它**全仓唯一用途**是
     `app/database.py` 的 SQL echo ⇒ 探针只要 `import app.database` 就把
     `sqlalchemy.engine.Engine` 行打进 stdout、污染输出。
     ⇒ 编排器 `_backend_env()` 加 `"DEBUG": "false"`（**不改任何 API 行为**）。

  🛡️ **新增常驻自检臂 `_check_live_db_honors_env()`**（编排器 `run_self_test()` 顶部）：
     临时造一张真 SQLite（含 `jobs` 表）→ 设 `DATABASE_URL` 指向它 →
     **断言 `resolve_live_db()` 返回的就是它**。已做**注入反证**：把 `resolve_live_db`
     换成忽略环境变量的版本 ⇒ 自检**正确报红**（控制组为 `[]`）。
     ⇒ 这条臂的意义：**「编排器设了 `DATABASE_URL`」≠「探针认了它」**，
       隔离必须是**事实性的**，不能只是声明式的。

     ⇒ 「绿的 12 条」现在**零阻塞**、可随时接线（仍待 §11.4-③ 的拍板）。
