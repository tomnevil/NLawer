0. 裁定：选 ①「让 AppShell 改用它」，不选 ②「删掉它」、不选 ③「维持现状」

理由（三条，全部有实测支撑）：

(a) **门禁本来就是为 ① 写的**，A1 / R2 / Q15 / I5 四处都指向接线：
    · A1 **硬要求** `tokens.css` 里有 `--page-pad` 且 == §4.2 现读的移动端值
      （`got is None` ⇒ `defects.append(...)` ⇒ **rc 1**）。⇒ 选 ② 删令牌，
      **A1 会转红并把它报成「产品缺陷」** —— 得先删掉一条判据。
    · R2 明写「要令牌化就得**新增一个令牌**」（已把 ① 当成预设路径）。
    · `--self-test` 的 Q15 / `--inject` 的 I5 专门断言「令牌化写法**必须绿**」
      （注释原话：「不逼死令牌化」）。
    ⇒ A1（要求令牌存在）+ R1（报它是死的）+ R2（要求补桌面令牌）三者
      **只在「① 接线」下自洽**；② 要靠删判据来收场。

(b) 同一个文件里就有**项目自己的、成文的**同类惯例 —— `tokens.css:261-269`：
    「断点写在这里而不是 Tailwind 类里，是为了让「288px」这类魔法数字在项目里
      只出现一次——组件只声明语义宽度。」⇒ `--page-pad` 的注释
    「移动端页边距（桌面 24px）」是**同一个意图的半成品**（缺媒体查询、缺消费者）。
    ① 是**把没做完的做完**，② 是**把意图删掉**。

(c) 消费者数 = 0 是**实测**（`frontend/packages` + `frontend/apps`，剪 `.next`/`node_modules`，
    且排除定义文件本身）⇒ 改它**确实**不改渲染 ⇒ 现状是**令牌在说谎**。
    按「响亮的缺席优于静默的谎言」，不能选 ③。

⚠️ 反方（诚实记录，仍然成立）：令牌化**没有可观测收益**（值不变、无人要求改版），
   且 `p-[var(...)]` 是任意值写法、绕开了 Tailwind 刻度。若日后要收窄，应改为
   preset 命名键（`spacing.pad` ⇒ `p-pad`，与 `w-rail` 同族）—— 那要动 preset，
   属另一项裁定。

1. 改动（2 个产品文件 + 1 个仪器文件）
--------------------------------------------------------------------------------

① `frontend/packages/ui/src/tokens.css`
   前：`--page-pad: 16px; /* 移动端页边距（桌面 24px） */`
   后：`--page-pad: 16px;` + `--page-pad-desktop: 24px;`（并补消费者/判据注释）
   ⚠️ 两个断点值分成**两个令牌**，而不是媒体查询翻转同一个 —— 因为 A2 要求内容区
      显式给出移动端值与 `lg:` 断点值（它不评估媒体查询）。想改成单令牌 + 媒体查询
      得先改 A2 的模型（仪器改动）。

② `frontend/packages/ui/src/components/AppShell.tsx:625`
   前：`className={cn("flex-1", padded && "px-4 py-4 lg:px-6 lg:py-6")}`
   后：`className={cn("flex-1", padded && "p-[var(--page-pad)] lg:p-[var(--page-pad-desktop)]")}`
   （`px`/`py` 合并为 `p`：原写法两轴同值，合并后仍是两轴同值，渲染不变；
     且避免出现「令牌叫 page-pad 却只管水平」的新一层谎言。）

③ `evidence/verify_page_padding.py`
   · 修 R2 的**潜伏缺陷**（见 §2）
   · 注入臂 I2–I5 重新锚定（原锚 `px-4 py-4 lg:px-6 lg:py-6` 在真仓库里已不存在
     ⇒ `replace_once` 会 AssertionError）；I5 **方向翻转**，继续证明
     「两种写法都必须绿（判据只认解析后的 px，不认写法）」。

2. 🚨 顺带逮到：门禁 R2 的 `--True` —— 一个**从未被执行过的分支**
--------------------------------------------------------------------------------

```python
has_desktop_token = any(          # ← any() 返回 bool！
    k for k in tokens if re.fullmatch(r"page-pad-(desktop|lg|desktop-pad)", k)
)
reports.append("R2 桌面档页边距令牌：" + (f"在（`--{has_desktop_token}`）" if has_desktop_token else ...))
```

· `any(...)` 返回 **bool**，不是键名 ⇒ `f"--{has_desktop_token}"` 打出 **`--True`**。
· **此前仓库里没有桌面档令牌 ⇒ 这个分支从未被执行 ⇒ 那句错话一直没人看见**
  （R2 是「只报不判」，永不让 rc 变红）。
· 2026-09-23 接线 `--page-pad-desktop` 时**第一次走到 `if` 分支**才暴露。
· 修：`next((k for k in tokens if ...), None)`。
· 实测证据：接线后首次运行打出 `R2 …：在（--True）`；修后打出 `在（--page-pad-desktop）`。

⇒ 教训（`methodology.md` #197）：**「只报不判」的报告行永远不会因为错而变红**，
  它的分支可能从写下那天起就没执行过。凡把一个条件分支接进「只报」路径，
  必须有一条自检臂**强制走 if 分支**（本例：`--self-test` 的 Q18 只覆盖了 else 侧）。

5. 🚨 关键验证：Tailwind **真的生成了**这两个任意值类
--------------------------------------------------------------------------------
（`p-[var(--x)]` 若没被生成，四端内容区内边距会**静默变成 0** —— 这是本改动唯一的
  真实风险，所以必须实测，不能靠「Tailwind 支持任意值」这句文档。）

5.1 CSS 规则（`curl http://localhost:3000/_next/static/css/app/layout.css`，dev 产物）

    .p-\[var\(--page-pad\)\]{
      padding: var(--page-pad);
    }
    …
    @media (min-width: 1024px){        ← 实测「最近 @media 在 line 3407」
      …
      .lg\:p-\[var\(--page-pad-desktop\)\]{
        padding: var(--page-pad-desktop);
      }
    }

  · 四端 **全部生成**（3000/3001/3002/3003 各命中 2 次 = 移动端规则 + tokens.css 注释）。
  · `@media (min-width: 1024px)` 与注释里写的「`lg:` 断点 = Tailwind 默认 1024px」一致
    （preset 的 `screens` 段只加了 `wide: "1600px"`，没有覆盖 `lg`）。

5.2 渲染 DOM（`curl http://localhost:3000/components-preview`，连续 3 次结果一致）

    <main class="flex-1 p-[var(--page-pad)] lg:p-[var(--page-pad-desktop)]"
          style="padding-bottom:calc(var(--tabbar-h) + var(--safe-bottom) + 16px)">

  · 内联 `padding-bottom`（有 TabBar 时）仍在，优先级高于类的 `padding` ⇒ 行为不变。
  · 页面里另有一处 `lg:px-6`，实测属于**顶栏**（`px-3 … lg:px-6` 的 header），
    不是内容区残留。

⇒ 计算内边距 = 移动端 16px / 桌面 24px，与改前**逐值相同** ⇒ 四端**零视觉变化**。
