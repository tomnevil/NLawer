2. 机制实测（**用项目自己装的那份 tailwind-merge**）
--------------------------------------------------------------------------------

  实装版本 **2.6.1**（⚠️ `package.json` 写的是 `^2.5.5` —— 锁定漂移，未深究）。
  跑法：`node -e "… require('…/frontend/node_modules/tailwind-merge') …"`（cwd = `frontend/`）

  | 输入 | 输出 | 结果 |
  |---|---|---|
  | `text-body-sm text-ink-900` | `text-ink-900` | 🚨 **字号被吞** |
  | `text-label text-ink-400` | `text-ink-400` | 🚨 吞 |
  | `text-caption text-ink-500` | `text-ink-500` | 🚨 吞 |
  | `text-h2 text-ink-900` | `text-ink-900` | 🚨 吞 |
  | `text-body-sm text-white` | `text-white` | 🚨 吞（标准色也一样） |
  | `text-body-sm text-body` | `text-body` | ✅ 正常（两个都是字号，后者胜） |
  | `text-body-sm leading-6` | 两个都在 | ✅ 正常（不同组） |

  ⇒ **根因**：twMerge 认不出本项目的语义档名（`body-sm`/`label`/`h2`…），
  于是把 `text-body-sm` 与 `text-<颜色>` 判成**同一组**；同一组里**后者赢** ⇒ 字号类被删。
  这是**最常见的组合**（字号 + 颜色），所以中招面很宽。

4. 🚨 必须先知道的：**判据测的不是「项目的 `cn()`」**
--------------------------------------------------------------------------------

  `verify_typography.py:249-256` 的 `twmerge_blocks()` 是这么拿 twMerge 的：

      const {twMerge}=require('tailwind-merge'); … twMerge.apply(null,x)

  ⇒ 它用的是**库的默认配置**，**完全没有读项目自己的 `frontend/packages/ui/src/lib/cn.ts`**。

  现状下两者**恰好一致**（`cn.ts` 就是 `twMerge(clsx(...))`，没有任何 `extendTailwindMerge`），
  所以**今天测出来的 63 条是真的**。

  🚨 **但一旦按「修法 A」改了 `cn.ts`，两者就分叉** ⇒ 判据**仍然报 63 条**
  ⇒ **棘轮永远红**（典型假红），而「已经修好了」与「没修」在 CI 里**长得一模一样**。

  ⇒ **结论：任何修法都必须同时改判据**（让它读项目的 merge 配置，或至少读 `cn.ts` 判断有没有扩展）。
    这一条与既有的「**判据的期望值一旦现读外部来源，就必须能表达『我读不到』**」同族
    （`methodology` / skill 陷阱 69）—— 这里的外部来源是**项目自己的合并配置**。

5. 三条修法与我的建议
--------------------------------------------------------------------------------

  **修法 A：改 `cn.ts`（+3~5 行 `extendTailwindMerge`）+ 同步改判据**

      const myMerge = extendTailwindMerge({
        extend: { classGroups: { "font-size": [{ text: SIZES }] } },
      });

  ✅ **库层面已验证有效**（同一批输入，改后 `text-body-sm text-ink-900` 两个都保留、
     `text-body-sm text-body` 仍正确地只留后者、去重正常）：
     `extendTailwindMerge` 实测结果 —— 见下表
  🚨 **代价**：那 **63 处**的渲染字号会**从「继承值」变成「声明值」**（作者本来就想让 `text-body-sm` 生效）
     ⇒ **四端视觉会变**，且可能连带 24 条 T2（行高按新字号重算）。
     ⚠️ 这是**修 bug**（让 UI 回到设计规范的字号阶梯），但**仍是视觉变更** ⇒ 需你拍板。

  **修法 B：不改共享包，逐个删掉被吞的类名（33 文件 87 处）**

  ✅ 渲染**零变化**
  🚨 留下 87 处「**作者意图没被表达**」的欠账（写了个不生效的类，删掉它只是把症状藏起来）；
     棘轮要么永远红，要么**提基线**（= 把欠账写进冻结值，正是「棘轮买到的是拦新增」那条边界）

  **修法 C（= A + 先做渲染基线）= 我的建议**

  ✅ 在 A 之前/之后各截一次**四端 26 页**的 computed `font-size`/`line-height`，
     出一张 before/after 差异表 ⇒ 「视觉会变」从**推断**变成**证据**，再合。
  ⚠️ 成本：需要真浏览器 + 四端 dev server ⇒ **这正是「浏览器 job」（#59）的第一块砖**，
     ⇒ 建议与 #59 **合并立项**，别单干。

  | `text-h2 text-ink-900` | `text-ink-900` 🚨 | **两个都保留** ✅ |
  | `text-body-sm text-white` | `text-white` 🚨 | **两个都保留** ✅ |

8. 【2026-09-24 追加】修法 C 第一步已执行：**渲染级差值实测**（你已选 C）
================================================================================

  新增探针 `evidence/probe_cn_render_delta.py`（**只测量、恒 exit 0**，已登记 `NON_GATE_SCRIPTS`）。
  做法：真 Chromium + CDP，在**四端免登录页**上，用**应用自己的全局 CSS**，
  临时插入两族 `<span>` 各读 `getComputedStyle().fontSize`：
    · A「今天」 = `class="text-ink-900"` —— 这正是**默认 twMerge 的输出**（字号被吞、只剩颜色）
    · B「修法后」= `class="text-<档> text-ink-900"`
  ⚠️ **不碰产品代码、不依赖数据库**（这是刻意的：并行会话正在改开发库，
     而 `visual_baseline.py` 的 before/after 必须在**同一数据指纹**下才可比）。

  **四端 body 计算字号 = `16px`（行高 `27.2px`），完全一致。**

  | 档 | 今天（类被吞） | 修法后（类生效） | 字号差 |
  |---|---|---|---|
  | `caption` | 16px | **11px** | **−5px（−31%）** |
  | `label` | 16px | **12px** | −4px（−25%） |
  | `body-sm` | 16px | **13px** | −3px（−19%） |
  | `body` | 16px | **14px** | −2px（−13%） |
  | `body-lg` | 16px | **15px** | −1px（−6%） |
  | `h4` | 16px | 16px | 0（巧合：`h4` 就是 16px） |
  | `h3` | 16px | **18px** | +2px（+13%） |
  | `h2` | 16px | **22px** | +6px（+38%） |
  | `h1` | 16px | **30px** | **+14px（+88%）** |
  | `display` | 16px | 16px | 0（**该档在产物 CSS 里根本不存在**） |

  行高也全变（`caption` 27.2 → 16.5px；`h1` 27.2 → 39px）。

  ⇒ **对修法 C 的意义**：`cn()` 修好之后的变化**不是微调** —— **10 个档里 9 个会变**，
    `h1` 高达 **+88%**、`caption` **−31%** ⇒ **强化**「必须先做渲染基线」的判断：
    直接改会让四端版式**大面积位移**。

  ⇒ **同时暴露两条边界**：
  1. ⚠️ **真实站点上「今天」的值不一定是 16px** —— 本表量的是 **body 上下文**的回退值；
     真实位置若祖先已设字号（祖先自己带 `text-body-sm` = 13px），回退值就是 13px。
     ⇒ 本表是**参考上/下界**，**不是**那 87 处的逐点实测。要逐点值必须登录 + 真实页面 +
     **稳定数据集** —— 这正是「浏览器 job」（#59）的地基。
  2. 🚨 **`display` 档在产物 CSS 里不存在** —— `verify_typography.py` 的 `CUSTOM_SIZES` 列了
     `display`，但 `.text-display` 没有定义 ⇒ 判据的档清单里有一个**设计系统里不存在的档**
     （当前无害：没有站点用它；但「档清单 ≠ 设计系统」值得单独核一次）。

  ⚠️ **另修掉一个我自己的静态假值**：我最初用 `grep -o "body{[^}]*}"` 读「body 基础字号」，
    得到 **14px**，并据此推断「回退值 = 14px」—— **错的**。
    `body{` 是 **`.text-body{` 的后缀子串**，grep 匹配到的是 `.text-body` 那条规则。
    **渲染实测的 16px 才是真值。**
    （同族：grep 家族的「子串 / 路径转换假阳性」；纪律仍是 **先实测 → 再解释**。）

  存证：`evidence/cn_render_delta_2026-09-24.txt`。

  **修法 C 剩下的一半（还没做）**：那 87 处**逐点**的 before/after，需要
  ① 登录四端 + ② 真实 26 页 + ③ **并行会话停手后的稳定数据集**。
  ⇒ 见第 6 节的边界与 `design-audit.md` §14.9。
