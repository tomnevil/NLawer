【2】依据：① 的真实成本（读码实测，不是估计）

读 `evidence/verify_buttons.py:706-789`（`run_render()`）与 `:160-172`（`APPS`）：

  这不是一条判据的接线，是一个**基础设施项目**。

【3】为什么**现在**不接 ①（五条，逐条可指）

  1. 🚨 **CI 从未真正执行过**。仓库当前**不是 git 仓库**（`git rev-parse` 报错）⇒
     只能靠 `ci.yml` 复核。现在写这个 job，**我无法验证它到底跑不跑得起来** ——
     而项目已经把这个反模式登记在案：
     「⚠️ **提错档 = 名册说接上了、实际没跑**」。
     ⇒ 在无法验证的通道上新增一条**永远没人看见它失败**的判据，是把「零判据」换成
       「假判据」，**比维持现状更坏**。

  2. **渲染半现在就是红的，而且存量一条没修**。`README.md` 坑 31 的实测结论：
     B5 ✗ **4 页**（`web /`、`web /knowledge`、`lawyer /dispatches`、`im /chat`）·
     B6 ✗ **21 条根因**（头像按钮 40×48 · 分页 `‹1›` 32×48 · 列表行标题 42px …）。
     ⇒ 接进 CI 会**立刻红**，只能上棘轮（冻结 25 条）。
     ⇒ 它买到的是「**拦住新增实例**」，**不是**「存量在被修」。

  3. **棘轮的价值窗口在债务清理期，不在现在**。B5/B6 的存量都属
     「组件层是好的、10 处实现绕过组件自己写高度」这一类；
     一旦开始清理，条数会成批下降 ⇒ 届时基线要反复收紧。
     现在冻结一个**没人打算动**的 25 条，收益低、维护成本是「每次 CI 红都要人判一次真假」。

  4. **成本与判据强度不匹配**。B5/B6 的**可静态部分已经判完了**（B1–B4 在棘轮里）。
     剩下的 B5/B6 恰恰是**渲染期概念**：README 坑 58 已实测「静态近似**不成立**」——
     按文件数 `variant="primary"` 会**第一天就 4 条假红**（条件渲染让同一文件里的 N 个
     primary 在任一时刻只渲染 0 或 1 个）。
     ⇒ 「每屏」只能靠渲染量，所以①的成本是**结构性**的，不是「多加一行 CI 配置」。

  5. **与 ② 合并后范围会膨胀**。② 的剩余部分（§8.1 / §8.2 的渲染级判据）是**同一个 job**：
     §8.1 ← `verify_component_wiring.py`；§8.2 ← `verify_appshell.py` / `verify_breakpoints.py` /
     `verify_mobile_375.py`。加上 `NOT_GATED` 其余渲染级探针，
     这个 job 的真实范围是 **13 个探针**，不是 1 个。
     ⇒ 它应该**一次性设计**（共享「起服务 + 播种 + 浏览器」的地基），
       而不是被 ⑧ 这一个条目拖着零散地接。

【5】本地按需跑：步骤（⚠️ **本次未执行**，命令**未实测**，别照抄）

为什么本次没跑（**环境原因，不是产品原因**）：

  · 需要**四端 dev server 同时在 3000–3003**；而沙箱的批量删除守卫是
    **按「回合」限流**的 ⇒ **一个回合只能成功拉起 1 个 `next dev`**
    （`MEMORY.md` 硬约束 2）⇒ 至少 4 个回合，或由用户手动开 4 个终端。
  · 实测内存：**Total 30.9 GB / Free 2.3 GB**（`node -e "os.totalmem()/os.freemem()"`）。
    ⇒ 按项目硬规则（批量操作前查内存、**< 8 GB 拒绝执行**）**明确不启动**；
      且**并行会话正在改 `methodology.md` 与后端文件**，同时起 4 个 dev server 会与之抢内存。
  · 2026-09-15 的事故（递归删除 → 窗口风暴 → 断电）就是内存/进程被榨干造成的，
    **不重复同一形状的操作**。

步骤（供内存充足时执行）：

  1. 起后端（8001）+ 使用已播种的 demo 库（四端账号见 §2）。
  2. 逐端起 dev server，**每个回合只起一个**；起法见 `MEMORY.md` 硬约束 2 的解法
     （`CODEBUDDY_SAFE_DELETE_BULK_STATE_DIR= …`，**删除仍进回收站**）。
  3. 跑门禁（**必须用 `backend/.venv/Scripts/python.exe` 且从仓库根**）：
       `backend/.venv/Scripts/python.exe evidence/verify_buttons.py`
       `backend/.venv/Scripts/python.exe evidence/verify_buttons.py --app web --path /knowledge`
  4. 结果落 `evidence/`（本目录），**不要落临时目录**。

  ⚠️ 若第 3 步得到 **EXIT=2**（「登录失败 ⇒ 整端未测」），那是**环境问题**，
     **不是**产品缺陷 ⇒ 不要写进缺陷清单。
