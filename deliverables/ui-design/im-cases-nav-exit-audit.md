## 1. 结论（先说）

`#39` 不是「探针太严」，是**真缺陷**，而且比原记录更精确：

**im 的 `/cases` 在 ≥1024 宽度下，只有当「当前分组没有案件」时才有一个指向 `/chat` 的链接；
一旦有案件，页面上就只剩指向自己的链接 ⇒ 用户被困在「我的案件」页。**

⇒ 受影响的是**恰恰最需要导航的人**（有案件、正在用产品的人）。

**推荐 ①**：把 `/chat` 与 `/me` **已经在用**的 `AppSwitcher` 补到 `/cases`
（以及根页 `/` 的头部）⇒ 出口**常驻**、与两条既有先例一致、**不触碰**任何未解的规范冲突。
⇒ 修完后 `verify_breakpoints.py` 的 **rc=1 → rc=0**，「2 条 rc=1」降到 **1 条（只剩 #72）**。

> 🚨 **§1 上面这段是「拍板前」的分析，其中两个前提已被实测推翻，勿照抄：**
> 1. **`AppSwitcher` 不是 `<a>`** ⇒ B2a 看不见它（B2a 取 `document.querySelectorAll('a[href]')`，
>    `verify_breakpoints.py:217`）；
> 2. **`/me` 也不是靠 `AppSwitcher` 通过 B2a 的** —— 它靠三格数据里的
>    `<Link href="/chat">`（`me/page.tsx:73,116`）。`/chat` 则靠常驻左列。
> ⇒ 结论（`/cases` 缺出口、必须补）**成立**；错的只是「补什么」。**修正后的手段见 §9。**

## 2. 判据要求什么（B2a）

`evidence/verify_breakpoints.py` 定稿的 **B2a**：

> **≥1024 必须有「导航出口」**：常驻左列（贴左、够高、宽 ≥ 200px）
> **或** 指向**其它**一级路由的站内链接。**自链不算出口。**

该判据的定稿过程本身就值得记：第一版写成「必须有可见 `aside`、宽 = 令牌」——
**那是「手段」不是「要求」**，把 im 的满屏三栏形态误判成缺陷（见探针 docstring `:50-62`）。
⇒ 现版本判的是**效果**（能不能离开这一页），这才是 §8.2 该行的实质。

## 4. 🚨 本轮新发现（比原记录更精确，也更要紧）

`cases/page.tsx` **全部只有两个 `href`**：

| 行 | `href` | 渲染条件 | 算不算出口 |
|---|---|---|---|
| `:147` | `/chat#new` | 🚨 **仅 `shown.length === 0 && group === "all"`**（空态 EmptyState 的 action） | 算，**但只在空态** |
| `:160` | `/cases/${c.id}` | 有案件时 | ❌ **自链**（一级段仍是 `cases`） |

⇒ **两个后果，第二个更严重**：

1. **缺陷是「状态相关」的**：有案件的客户在 ≥1024 下**必然被困**；
   没有案件的客户反而**能**离开（空态那个「发起咨询」按钮）。
   ⇒ **缺陷恰好命中活跃用户**。
2. 🚨 **判据结论依赖种子数据**：同一个探针，种子库**有**该用户的案件 ⇒ **红**；
   **没有** ⇒ **绿**。⇒ **这不是一条确定的判据**。
   这与本项目既有纪律冲突（「判据的结论不应依赖运行时数据」）——
   即「同一份代码，两套种子库给出两个结论」= **判据本身的不确定性**。

⇒ ② 让 ① 的价值翻倍：把出口做成**常驻**，**同时**消掉缺陷**和**判据的数据依赖。

## 6. 推荐 ① —— 理由

1. **它是「对齐」而不是「新设计」**：`/chat` 与 `/me` **已经在用** `AppSwitcher`，
   `/cases` 是四条路由里**唯一的例外** ⇒ 补上它 = **消除不一致**，
   **不引入任何新的设计语言、不改动共享包、不新建规范条目**。
2. **它不触碰规范冲突**：③ 才需要先解「决策 05 vs §8.1 / 决策 12」；
   ① 是在**现有形态（满屏三栏 / 非 AppShell）内**补齐出口。
3. **它一次解决两个问题**（见 §4）：缺陷 + 判据的数据依赖。
4. **它可判且会自然归零**：修完 B2a 四条路由全绿 ⇒ `verify_breakpoints.py` **rc=1 → rc=0**，
   **不需要棘轮、不需要白名单**，且「2 条 rc=1」降到 **1 条**。

## 9. 🚨 落地记录（2026-09-25）：① 的前提被实测否掉，改用 ① + ②

### 9.1 第一轮实测：① 原样落地 ⇒ **仍然 rc=1**

改动（`cases/page.tsx` 与根页 `page.tsx` 头部各挂一个 `AppSwitcher`）之后，四端实测：

```
▸ python evidence/verify_breakpoints.py
  ❌ rc=1 · **产品缺陷** · 57.9s
      expanded 起点（=1024，切换点） @/cases ✗
          [B2a 1024px] ≥1024 时既无常驻左列，也没有指向**其它**一级路由的链接
          （页内链接=['cases']）⇒ 该宽度下**没有导航出口**
```

**`页内链接=['cases']` 是关键证据**：加了 `AppSwitcher` 之后，B2a 采到的链接**一个都没多**。

### 9.2 根因：`AppSwitcher` 不产出 `a[href]`

`packages/ui/src/components/AppSwitcher.tsx`：

- `:82` 根元素是 `<div className="relative">`，`:83` 是 **`<button>`**（`aria-haspopup="menu"`）；
- `:116` 菜单是 **`{open && canSwitch && (…)}`** —— **未点开时根本不在 DOM 里**；
- `:127` 菜单项也是 **`<button role="menuitem">`**，**不是 `<a>`**。

而 B2a 取的是（`verify_breakpoints.py:217`）：

```js
[...document.querySelectorAll('a[href]')]   // 只认 <a href>，且 href 以 "/" 开头
```

⇒ **两条独立原因**让 `AppSwitcher` 对 B2a **完全不可见**：① 不是 `<a>`；② 不是常驻渲染。

### 9.3 同时被推翻的第二个前提：`/me` 也不是靠 `AppSwitcher`

`me/page.tsx:71-76` 的三格数据里，第 2 格是 `{ key: "convs", …, href: "/chat" }`，
`:116` 把它渲染成 **`<Link href="/chat">`** ⇒ **这才是 `/me` 过 B2a 的原因**。

⇒ 原 §3 表格里「`/me` 的出口 = `AppSwitcher`」是**读码推断的错**（`grep AppSwitcher` 找到了它，
就假定它承担了出口）—— 与用户级记忆里「**读源码得出的结论也要回头用一次实测确认**」同型。

### 9.4 最终手段：① + ② 并用

| 改动 | 作用 | 满足 B2a？ |
|---|---|---|
| `cases/page.tsx` / `page.tsx` 头部保留 **`AppSwitcher`** | **跨端切换**（与 `/chat` `/me` 一致），产品价值独立存在 | ❌ |
| `cases/page.tsx` 头部新增 **`<Link href="/chat#new">发起咨询</Link>`** | **常驻导航出口** | ✅（`chat` ≠ `cases`，非自链） |

`<Link>` 放在 `h1` 同一行右侧（`flex items-baseline justify-between gap-3`），
措辞与目标**沿用空态与根页已有的同一入口**（不新造第二种说法）。
⚠️ 带可见文字的链接**不在** `verify_tap_targets.py` 范围内（它只扫「有 svg 且无可见文字」的图标按钮）
⇒ 不引入 48px 热区缺陷。

### 9.7 教训（可复用）

1. **「出口」≠「能离开」**：判据只认一种手段（`a[href]`）时，任何「看起来像出口」的组件都要
   **先用判据验证**，别用「它语义上是导航」去推断。
2. **下拉组件天然不是出口**：`{open && …}` 的渲染方式决定它对任何静态取数都不可见。
3. **先例要验、不要数**：`grep` 到某组件在别处出现过，不等于它在别处**承担了那个职责**。
