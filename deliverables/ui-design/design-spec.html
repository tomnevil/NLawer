00现状诊断

在动工之前，先把「现在差在哪」说清楚。以下结论来自对 frontend/ 全部 38 个 TSX 页面与 packages/ui 14 个组件的通读。

0.1 八个结构性问题

#问题证据与影响
01导航体系缺失 Sidebar 组件已实现但几乎未被使用；4 个 app 各自用自造 header，页面之间靠 URL 手写跳转，用户无法感知「我在哪、还能去哪」。首页是「大卡片门户」而非工作台，进入任一功能需先返回首页。
02视觉语言自相矛盾 首页用深色渐变底（indigo-950 → indigo-800）+ 白卡片，内页却是浅色 slate-50 + 白 header。同一个产品在两种视觉体系间反复横跳。
03品牌色失去层级 from-indigo-600 to-cyan-500 渐变被同时用于主按钮、用户气泡、进度条、图标块、登录左栏。渐变一旦无处不在，就等于没有重点。
04语义色名实不符（危险） theme/colors.ts 中键名 emerald 实际值是靛蓝、teal 是青色、cyan 是紫色。KpiCard color="emerald" 渲染出的是蓝色。任何按语义取色的新代码都会踩坑。
05深色模式是补丁 globals.css 用 20 余条 !important 硬覆盖 Tailwind 工具类。新增任何颜色类都会漏网，维护成本随页面增长线性上升。
06责任边界表达太弱 PRD 强调「AI 生成 / 律师确认」边界，但实现只有一条 3px 左边框 .ai-content，且仅出现在流式输出中。用户无法一眼分辨哪段结论可依赖。
07引用溯源交互倒退 法条引用以弹窗抽屉（CitationDrawer）呈现，遮住正文。法律问答的核心场景是「边读结论边核对法条」，弹窗恰恰破坏了这个场景。
08缺少专业组件 没有 Tabs、Drawer、Timeline、Stepper、DataTable（排序/筛选/列设置/密度）、Pagination、SegmentedControl、CitationChip、ProvenanceBadge。法律产品最核心的「证据时间线」「复核流转」「案号等宽对齐」全部缺失。

0.2 改造前后对照

改造前 · 现状

  • 首页是「5 张大卡片」导航门户，进功能要来回跳
  • 靛蓝→青色渐变铺满按钮、气泡、进度条
  • 圆角 rounded-xl / 2xl / 3xl 偏软，缺少专业硬度
  • 深色侧栏 indigo-950 与内容区 slate-50 冷暖不一致
  • 法条引用弹窗遮挡正文
  • AI / 律师确认边界仅一条紫边线
  • 深色模式靠 !important 覆盖
  • 表格无排序、无筛选、无密度控制

改造后 · 本规范

  • 统一 AppShell：240px 墨色侧栏 + 56px 顶栏 + 内容区，四端一致
  • 品牌色收敛为单一墨蓝，渐变仅用于登录页品牌区
  • 圆角收敛到 4 / 6 / 8 / 12，回归方正克制
  • 墨蓝 #0A1830 侧栏 + 中性灰内容区，同一色温
  • 引用溯源改为常驻右侧面板，正文不被遮挡
  • 三态责任边界系统 + 全局图例
  • CSS 变量 + 语义 token，深色模式零覆盖
  • DataTable 含排序、筛选、列设置、三档密度
关于工作量：这不是一次「换皮」。00-04 节属于基础设施改造（约 60% 工作量），05-07 节是页面重构。 建议按第 08 节的四阶段推进，每个阶段结束都有可交付、可回滚的完整状态。

01设计定位与原则

关键词：可信（Trustworthy）、克制（Restrained）、密实（Dense）、可追溯（Traceable）。

原则一 · 信任优先于惊艳

法律产品的用户把重大权益托付给系统，界面需要传递「稳」。因此：不用大面积渐变、不用发光阴影、不用卡通插画；用留白、对齐、克制的色彩和清晰的信息层级建立信任。

原则二 · 边界必须可见

AI 生成什么、律师确认了什么、哪些还没复核——这必须成为视觉系统的一等公民，而不是一条边线。任何一段法律内容都必须携带可识别的责任状态。

原则三 · 信息密度是美德

律师每天处理几十份材料，界面应承载信息而非消耗屏幕。放弃大卡片门户，改用侧栏 + 密集列表 + 表格；一屏内尽量呈现完整的决策依据。

原则四 · 数字与案号必须对齐

金额、案号、日期、条款编号全部启用等宽数字（tabular-nums）与等宽字体。这是法律文书校对的基本要求，也是专业感的直接来源。

1.1 与现有品牌的关系

本规范保留靛蓝作为品牌识别锚点，但把它沉到墨蓝区间（#4F46E5 → #274C93）。理由：

  • #4F46E5 是典型的「AI 初创」色，明度高、饱和度高，大面积使用显得轻；
  • #274C93 与之同色相，视觉识别连续，但明度降低 34%、饱和度降低 21%，更接近律所、法院、金融的信任色域；
  • 点缀色引入香槟金 #B08A4F（S 级案件、引用序号、付费标识），替代原先的亮金 #F5B942——后者过于跳脱，像促销标签。
若你希望保留原靛蓝：可执行「最小改动方案」——只做第 01、04、05、06 节（导航体系、间距圆角、责任边界、组件）， 色彩仅把 cyan 渐变从按钮上撤下。这会省下约 25% 工作量，但视觉提升幅度也相应减半。

04布局 · 间距 · 圆角 · 阴影

4.1 全局框架（AppShell）

四个应用共用同一套骨架。这是解决「导航体系缺失」的核心手段。

AppShell 结构

左侧 240px 墨色导航（可折叠至 64px）· 顶部 56px 栏（面包屑 + 全局搜索 ⌘K + 通知 + 用户）· 内容区最大宽 1280（工作台）/ 1600（驾驶舱）。侧栏顶部含应用切换器，打通 web / lawyer / admin 三端，替代当前靠手输 URL 的跳转方式。

  • 左侧色条：责任边界标识（3px 实线）
  • 焦点环：0 0 0 3px rgba(54,96,176,.22)，全局统一

05责任边界三态系统

这是本规范相对现状提升最大、也最能体现产品价值的部分。PRD 反复强调 AI 与律师的责任划分，但界面上几乎不可见。我们把它提升为一等视觉语言。

5.1 三种状态

AI 生成内容由模型产出，尚未经人工核验。使用：紫色虚线上边框 + 浅紫底 + 左上角 ✦ AI 生成 徽章。
律师已确认执业律师已复核并签署。使用：绿色实线左边条 3px + 浅绿底 + ✓ 律师已确认 徽章，并附带确认人与时间。
待复核 / 风险已生成但存在风险或等待人工介入。使用：琥珀色左边条 + 浅琥珀底 + ⏱ 待复核 徽章。

5.2 使用规则

  • 穷尽性：任何一段法律内容（结论、条款、分析、建议）必须且只能属于三态之一，不允许「无状态」内容。
  • 全局图例：在问答页、文书页、案件详情页顶栏常驻三态图例（见 7.3 概念图），让用户无需学习即可理解。
  • 状态可迁移：AI 生成 → 律师确认 是单向、留痕的。状态徽章需可点击查看流转记录（谁、何时、改了什么）。
  • 导出保留：导出 PDF / Word 时，三态标记必须保留（页脚水印或段落标记），这是法律文件的合规要求。
  • 颜色不可独立承载语义：必须「颜色 + 文字 + 图标」三重编码，保证色盲与黑白打印可用。
与现状的差距：当前仅有 .ai-content { border-left: 3px solid #8b5cf6; background: #f5f3ff } 一条规则， 且只在流式输出阶段出现，回答完成后即消失。.lawyer-confirmed 定义了但全站零处引用。

08移动端设计规范

法律服务的真实使用场景大量发生在手机上：客户半夜遇到纠纷先掏手机问一句、律师在法院走廊等开庭时翻案卷、 企业法务在会议室里核对条款、HR 在招聘现场拍一份劳动合同回来扫描。移动端不是「桌面端的缩小版」，而是需要独立设计的第二主场。

本规范的立场：移动端优先（Mobile First），但不是所有页面都要移动化。 运营驾驶舱的复杂图表、文书编辑器的长文排版仍以桌面为主；而咨询、问答、案件阅读、证据上传、复核审批—— 这些高频、碎片、移动场景明确的动作必须原生适配移动端。

8.1 各端移动端优先度

端移动端定位必须移动适配的功能
im（客户端） 移动优先 全部。C 端客户几乎只用手机。设计基准直接按 375px 起草，桌面端视为放大适配
web（企业法务） 移动优先 登录、工作台、问答、合规扫描（拍照即扫）、案件进度、通知、我的。文书编辑器仅支持移动端预览与批注
lawyer（律师端） 移动强需求 派单池（抢单）、案件阅读、证据拍照上传、复核审批、沟通记录、工时填报。卷宗整理以桌面为主
admin（运营后台） 桌面为主 仅支持只读查看：驾驶舱核心指标、告警、案件查询。批量操作、规则配置不移动化

8.2 断点与布局切换

断点宽度导航形态内容区
compact< 640px底部 Tab Bar + 顶部 AppBar单列，页边距 16px；表格转卡片
medium640 – 1023px底部 Tab Bar（平板可改侧栏图标态）单列为主，允许两列卡片；页边距 24px
expanded1024 – 1599px侧栏 240px 常驻12 栅格，页边距 24px，内容最大宽 1280
wide≥ 1600px侧栏 240px 常驻驾驶舱全宽（1600），其余保持 1280

⚠️ 修订（2026-09-23）：wide 原写 ≥ 1440px、expanded 原写 1024 – 1439px，与 §4.2「断点 640 / 1024 / 1280 / 1600」及 tailwind.preset.ts 的 screens.wide = 1600px 自相矛盾（1440 在实现里根本不存在 —— 全仓 wide: 工具类 0 处）。现按 1600 对齐（1600 有三处实现支撑：screens.wide / maxWidth.wide / --content-wide），并把 expanded 上界一并改为 1599，以消除 1440–1599 的空档（只改 wide 会留空档）。

关键规则：侧栏在 < 1024px 时不折叠成 64px 图标条，而是完全收起为抽屉—— 64px 图标条在手机上仍然占用宝贵宽度，且图标无语义提示时难以辨认。

8.3 触控目标与拇指热区

触控目标尺寸

  • 最小 44 × 44px（Apple HIG / WCAG 2.5.5）
  • 本项目标准 48 × 48px——法律产品用户年龄跨度大，含 45+ 律师与客户
  • 列表行高 ≥ 48px；主按钮高度 48px
  • 相邻可点元素间距 ≥ 8px，避免误触
  • 图标按钮必须有 48px 的不可见热区，即使图标只有 20px

拇指热区

  • 底部 1/3：主操作、Tab Bar、输入框
  • 中部：内容阅读区
  • 顶部：仅放标题、返回、低频操作
  • 「AI 提问」入口放在首页首屏中下部，不放在顶部
  • 破坏性操作（删除、退回）不放在右手拇指自然落点

安全区与手势

  • 所有固定底部元素加 env(safe-area-inset-bottom)
  • 顶部状态栏区域留 44px（刘海屏 / 灵动岛）
  • 底部横向手势区（Home Indicator）高 34px，不放可点元素
  • 支持左滑返回；右滑不绑定操作

8.4 导航模式

三种移动导航形态

客户端 4 项 Tab、律师端 5 项 Tab（派单池带红色待办角标、待同步带琥珀角标）、运营后台仅只读。 律师端额外有常驻底部操作条——办案过程中「确认本段」「提交复核」需要随时可点，不能藏在菜单里。

Tab Bar 的取舍：iOS 规范建议不超过 5 项。律师端正好 5 项（工作台 / 派单池 / 案件 / 复核 / 我的）—— 「归档」「工时」「模板库」等次级功能收进「我的」或工作台的快捷入口，不塞第 6 个 Tab。

8.5 表格转卡片规则

桌面端的数据表格在移动端无法使用。转换规则如下，开发时按列数自动判定：

桌面表格特征移动端形态转换规则
列数 ≤ 3，行数 ≤ 8保留表格隐藏表头，用首列 + 右侧值的形式展示
列数 4 – 6卡片列表（首选）主标识 + 状态徽章置顶；其余字段两列网格排布；操作按钮置于卡片底部
列数 > 6卡片列表 + 详情页卡片只保留 3 个关键字段，其余进详情页
需要横向对比数值横向滚动 + 首列冻结仅在驾驶舱等强对比场景使用，必须显示滚动提示

案号、金额、日期在移动端仍保持等宽字体，但字号可降至 11–12px 以节省宽度。

8.6 弱网与离线

律师在法院、看守所、地下停车场经常没有信号。这是法律行业特有的、必须在设计阶段就解决的场景。

离线可读

  • 打开案件时预缓存六段式分析、证据索引、文书正文（单案上限 20 MB）
  • 缓存状态在证据列表用 ✓ 明示，用户知道哪些能离线看
  • 离线模式下顶部显示琥珀色状态条，并提供「重试」入口

待同步队列

  • 离线期间的拍照、批注、状态变更全部进队列，不报错、不丢失
  • 队列项显示进度与状态（上传中 / 等待）
  • 恢复网络后自动补传，并在 Tab 角标上用琥珀色区分「待同步」与「待办」（红色）
  • 冲突处理：以服务端为准，本地变更保留为批注草稿
