## 0. 先说三件必须更正的事

### 0.1 我上轮把「实现成本低」说错了

上轮我把 #15 描述为「规范已明写 4 项，**实现成本低**」。**这是错的**，理由见 §2：
im 只有 **1 个路由**，4 项 Tab 里有 3 项**没有落地页**。成本不是「接线」，是「建页 + 拆分路由 + 桌面端形态决策」。

### 0.2 我上轮报的「im 零响应式断点」是**工具假阴性**

上轮我用 `grep -n "lg:\|md:\|sm:\|hidden\|..."` 得到空结果，据此说 im「零断点」。
**实测推翻**：`lg:` 在该文件出现 **6 次**（`grep -c "lg:" → 6`）。

根因是 **Git Bash 的 MSYS 路径转换**：

```bash
grep -c 'lg:\|hidden'  file   # 命中 0 —— 假阴性
grep -c 'hidden\|lg:'  file   # 命中 10 —— 正常
```

`lg:` 紧跟 `\|` 时，MSYS 把 `lg:\` 当成**盘符**，把反斜杠转成正斜杠 ⇒
正则变成字面量 `lg:/|hidden` ⇒ 永远 0 命中。**是 `:` 后面那个反斜杠被吃掉，不是模式写错。**

> 教训与本项目已有的「`taskkill //F` 被 MSYS 改写」是**同一族**问题。
> **凡 grep 返回 0，先确认模式里的反斜杠没被路径转换吃掉**——
> 尤其模式里含 `字母:` 或 `/` 时。用 `MSYS_NO_PATHCONV=1` 或把该分支单独 grep。

### 0.3 `08-mobile-client.html` 的内容是**企业法务**，不是 C 端客户

§8.7 把 08 稿标为「移动端（**客户 / 企业法务**）」。但逐屏核对正文：

| 屏 | 稿内实际文案 | 归属 |

## 2. 现状实测

### 2.1 路由

```
apps/im/app/
├── (app)/layout.tsx     ← 受保护外壳（h-dvh + overflow-hidden + 四边安全区）
├── (app)/page.tsx       ← 1304 行，三栏 IM 工作台（= 咨询）
└── login/page.tsx
```

**只有 1 个业务路由。** 对照：web 7 个、lawyer 7 个。

### 2.2 移动端已有形态：下钻，不是 Tab

`page.tsx` 有 6 处 `lg:` 断点与一个视图状态机：

```tsx
const [mobileView, setMobileView] = useState<"list" | "chat">("list");
// 左栏：mobileView === "list" ? "flex" : "hidden"          （移动端二选一）
// 右栏：mobileView === "chat" ? "flex" : "hidden lg:flex"  （桌面端常驻）
```

⇒ 移动端是**会话列表 → 会话详情**的下钻（有 `lg:hidden` 返回键）。
**能用，但它只能下钻到会话内部**：进去以后**没有任何出口**通向「我的案件」「我的」——因为那两页不存在。

### 2.3 桌面端为什么不用 AppShell（既有决策，本稿沿用）

`(app)/layout.tsx` 的注释写得很明确：

> 概念图 06 把 IM 定为**满屏三栏**：288px 会话列表 + 正文 + 320px 案件上下文。
> 而 AppShell 在 ≥1024px 时会常驻一条 240px 墨色侧栏，两者叠加后 1280px 屏幕上
> 留给正文的只有 432px——一段法条原文都放不下。

⇒ **桌面端不能套 AppShell 的常驻侧栏**。这是本稿 §6 的核心约束。

### 2.4 缺口的三层（由浅到深）

| 层 | 缺口 | 严重度 |
|---|---|---|
| L1 | 移动端**无底部 Tab Bar** | 违反 §8.4 |
| L2 | 4 项 Tab 里**3 项没有落地页**（工作台 / 我的案件 / 我的） | 违反 §8.1「移动优先」 |
| L3 | **C 端客户的移动端设计稿不存在**（08 稿是企业法务的） | 设计资产缺口 |

**L1 单独修没有意义**：接上一个指向不存在路由的 Tab Bar，只是把 404 摆到拇指边上。

## 4. 路由映射方案（建议）

`AppLayout` 的 `activeId = pathname.split("/").filter(Boolean)[0] ?? rootId`，
所以 **tab id 必须等于一级路径段**（`/` 用 `rootId`）。据此：

| # | Tab | 路由 | 落地页 | 状态 |
|---|---|---|---|---|
| 1 | 工作台 | `/` | **新建** | 待建 |
| 2 | 咨询 | `/chat` | **搬迁**（现有 `page.tsx` 1304 行） | 待搬 |
| 3 | 我的案件 | `/cases` | **新建** | 待建 |
| 4 | 我的 | `/me` | **新建** | 待建 |

```ts
const TABS: TabBarItem[] = [
  { id: "home",  label: "工作台",   href: "/" },
  { id: "chat",  label: "咨询",     href: "/chat" },
  { id: "cases", label: "我的案件", href: "/cases" },
  { id: "me",    label: "我的",     href: "/me" },
];
```

**搬迁的爆炸半径（已 grep）**：全仓只有 2 处引用 im 地址，且都是**裸 base URL**
（`evidence/mobile_preview.py:17`、`frontend/packages/ui/src/lib/apps.ts:26`），
**没有任何深链指向 `/`** ⇒ 搬迁风险低。

## 6. 实现要点（定稿后照此施工）

### 6.1 TabBar 接入方式

`TabBar` 组件已存在且**自带 `lg:hidden`**（`packages/ui/src/components/TabBar.tsx:36`）
⇒ 桌面端自动不渲染，**不需要额外判断**。

### 6.2 ⚠️ 安全区会被**双重计算**（必须处理）

`(app)/layout.tsx` 根容器已有 `paddingBottom: var(--safe-bottom)`；
而 `TabBar` 内部也加了 `paddingBottom: var(--safe-bottom)`。

⇒ 直接接入会在底部**多出 34px 空白**（iPhone 安全区）。
处理：**TabBar 存在时，根容器去掉 `paddingBottom`**，改由内容区用
`padding-bottom: var(--actionbar-bottom)` 预留——该令牌**已存在**
（`tokens.css:200`：`calc(var(--tabbar-h) + var(--safe-bottom))`），无需新增。

> 这是本项目「`dvh` / 媒体查询这类由浏览器解析的改动，静态门禁全覆盖不到」的又一例，
> **必须做渲染级验证**（390×844 下量底部留白）。

### 6.3 高度与滚动

im 是三栏各自滚动、页面本身不滚动（`h-dvh overflow-hidden`）。
加 Tab Bar 后**页面级高度不变**，只是内容区底部少 56px——**不能**改成 `min-h-dvh` 让页面滚动，
否则会丢掉「三栏各自滚动」这个核心体验。

#### 🚨 生产构建这一步抓到一个**此前从未被发现**的真缺陷

`packages/sdk/src/index.ts:28`：

```ts

  (process.env.NEXT_PUBLIC_API_BASE) || "http://localhost:8000";
```

兜底串是 **`:8000`**，而后端在 **`:8001`**。`NEXT_PUBLIC_*` 是**构建期内联**的，
所以 `.env.local` 一缺，Next **不报错**：`next build` exit 0、路由 HTTP 200、
`!important` / 色系 / 令牌**全部照过**——只有浏览器里「点登录毫无反应」。

**实测**：`apps/im/.env.local` **从未被创建**（web / lawyer / admin 三端都有，
且 `.env.local` 在 `.gitignore` 里）。im 的 dev server 之所以一直正常，
是因为**启动命令里 export 了该变量**；而 `_prev_build/im-prod-build-102012`
那份**被记为「已验证通过」**的生产产物，其实烘的是 `:8000` ——
**它从来没有能力连上后端，而当时的所有门禁都放过了它。**

处置：
1. 补 `apps/im/.env.local`（与另三端一致）并**重新构建**；
2. 补门禁 `evidence/verify_api_base_baked.py`（自检直接用归档的那两份坏产物当对照 ⇒ 报「会红」）；
3. 重跑：安全区 `EXIT=0`、四 Tab + 桌面三栏 `EXIT=0`、运行时健康 im 5 页 `0 问题` ——
   **这一次全部是在 `next start` 的生产产物上测的**，不再是 dev。

**两条必须记下来的修正**（都是「我的判据错了，不是产品错了」）：

1. **参照面要取 TabBar 的「内容顶」，不是「边框顶」。**
   `TabBar` 自带 `border-t`（1px），所以它的 border-box 比 `--tabbar-h` 高 1px。
   第一版拿「边框顶」做参照，于是正确实现被测成 `gap = -1px`，看起来像「内容被压住」。
   真相是：内容**应该**正好铺到按钮区顶边，由 TabBar 自己那 1px 边框压住这条缝——
   有边框的固定条就是这么画的。⇒ 判据改成 `gap = nav.top + borderTopWidth - contentBottom`，
   正确实现**精确**为 `0`，双算**精确**为 `34`，两者不再互相混淆。

2. **`tokens.css:244` 有一条 `@media (max-width: 1400px)` 把 rail/panel 收窄**
   （288→250、320→280）。第一版只在 1280px 测、却按 288/320 断言 ⇒ 报出 **2 条假缺陷**。
   改测两档后，「按断点收窄」这件事本身也变成了一条被锁住的断言。

3. **别拿「正文多少字」判空壳。** 客户端的会话数就是 **0**，`/chat`（73 字）与 `/me`（114 字）
   本来就短。第一版用「< 120 字即空壳」⇒ 又把**合法的空状态**报成 2 条假缺陷。
   改成结构判据：内容区里真的挂上了页面组件 + 无框架错误边界 + 标志文案在。
   > 合计 **4 条假红**。这正是「证据工具须区分『产品坏了』与『我没测成』」要挡的东西——
   > 如果我直接把那 4 条报给你，就是在拿自己的判据错误去指认产品缺陷。
