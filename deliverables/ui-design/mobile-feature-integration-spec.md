## 0. 先说三件必须先讲清的事

### 0.1 「拍照即扫」（web）在**后端冻结**的前提下做不了 —— 需后端配合

§8.1 点名要求 web「**合规扫描（拍照即扫）**」。实测后端能力：

| 端点 | 入参 | 能否服务「拍照即扫」 |
|---|---|---|
| `POST /api/v1/compliance/scans` | **JSON 文本**（`ComplianceScanCreate`：`title` / `dimensions` / `scope` / `input_summary` / `is_external`） | ❌ **不接受文件** |
| `compliance.py` 全部路由 | 仅 3 个：`POST /scans`、`GET /scans`、`GET /scans/{scan_id}` | ❌ **无任何附件端点** |
| OCR 能力 | 仅 `app/services/evidence_service.py:69` 的 `_mock_ocr()`（占位实现） | ❌ 且**绑定在案件证据上** |

**为什么 OCR 借不过来**：`_mock_ocr()` 的产物写在 `Evidence.ocr_text` 上，而 `ComplianceScan`
**没有 `case_id`**（见 `ComplianceService.create_scan` 的入参）——合规扫描与案件证据是两条线，
没有可复用的通路。

⇒ 「拍照 → 出文本 → 喂给扫描」**缺后端能力**。要么新开端点（接受图片并 OCR），
要么让 `/compliance/scans` 接受附件。**后端已冻结 ⇒ 登记为「需后端配合」，本轮不做。**

> 这不是新结论——`§9「✅ 重写 tailwind.preset.ts」` 自己就写着：
> 「弱网与离线能力（预缓存、待同步队列、自动补传、冲突处理）—— **后端也要配合**」。
> 本稿只是把「哪一条缺、缺在哪」实测出来了。

### 0.2 SDK 现在**发不出 multipart** —— 这是硬前提，不是实现细节

`packages/sdk/src/index.ts`（446 行，**唯一源文件**）的 `request()` 有两处**无条件**处理：

```ts
// l.249
if (opts.body !== undefined) headers["Content-Type"] = "application/json";
// l.286
body: opts.body !== undefined ? JSON.stringify(opts.body) : undefined,
```

传 `FormData` 会**同时**出两个错：

1. `Content-Type` 被写死成 `application/json` ⇒ 浏览器**不再补** `multipart/form-data; boundary=...`
   （`boundary` 只能由浏览器生成，手写不出来）；
2. `JSON.stringify(FormData)` 的返回值是 **`"{}"`** ⇒ body 变成一个空 JSON 对象。

⇒ 后端 `file: UploadFile = File(...)`（`evidence.py:49`）会直接 **422**。

**全仓核对**：`packages/sdk` 内 `upload` / `FormData` / `evidence` 三个词**命中 0**——
SDK 是一层纯 JSON 的薄 HTTP 客户端（`request` / `http` / `streamSSE` / `authed` / `login` /
`logout` / `restoreSession` + 令牌与租户存取），**没有任何领域方法与上传能力**。

⇒ **必须先给 SDK 加一个 `upload()`**（复用鉴权 / 401 刷新 / 租户头 / CSRF，
但**不设 `Content-Type`、不做 `JSON.stringify`**）。属前端改动，可以做。

> 为什么不「各端自己写 `fetch`」：那会把 401 自动刷新、`X-Tenant-Id`、CSRF 头
> 三件事在三个端各抄一遍——正是本项目已经踩过的「契约层抄多份」缺陷
> （见 `MEMORY.md` 关于 `apps/im/lib/imApi.ts` 的记载）。

### 0.3 阶段二的「验收」验收的是**预览页**，不是产品页

`§8.3「破坏性操作（删除、退回）不放右手拇指自然落点」` 原文：

> ✅ 新建 `apps/web/app/components-preview` 页面逐一验收视觉，**该页同时是 AppShell 的集成验证**

⇒ **阶段二没有漏做**——它的验收对象**本来就是预览页**。缺的是**阶段三的页面重构**
（`§8.3「支持左滑返回；右滑不绑定操作」`「阶段三 · 页面重构」）。

⇒ 所以 #20 的正确表述是「**阶段三未覆盖这三个组件**」，而不是「阶段二没做完」。
这个区分很重要：它决定了这件事是**补做**还是**从未排期**——是后者。

## 5. 落地方案 B：`PullToRefresh` / `InfiniteList`

### B.1 `PullToRefresh` 接入点（建议 3 处）

| 位置 | 理由 | 优先级 |
|---|---|---|
| `NotificationCenter` 的移动 BottomSheet | **NR-11 点名**「支持下拉刷新」；且它是通知中心，刷新是主行为 | **P0（规范要求）** |
| im `/chat` 会话列表 | C 端客户最高频页面；会话由对方产生，**只有下拉才能主动获取新消息** | P1 |
| im `/cases` + lawyer `/cases` | 案件状态由律师/运营推进，客户侧只能等；下拉是唯一的「主动确认」手段 | P1 |

> ⚠️ **为什么不给 im `/me` 加**：那是静态设置页，没有「新数据」可言，加了下拉刷新
> 只会得到一个永远不变的手势——**装饰性交互**。

#### 🚨 施工前置条件：NR-11 那处**不是一行接线**（实测，2026-09-20）

`BottomSheet` 与 `PullToRefresh` **各自带滚动容器**：

| 组件 | 滚动容器 |
|---|---|
| `BottomSheet` | `BottomSheet.tsx:170` **硬编码** `scroll-thin min-h-0 flex-1 overflow-y-auto px-4 py-4` |
| `PullToRefresh` | `PullToRefresh.tsx:126-132` 自带 `ref={scrollRef}` + `overflow-y-auto overscroll-contain` |

`PullToRefresh` 的手势守卫是 `if (el.scrollTop > 0) return`——它**假设自己那个容器就是真正在滚的那个**。
若真正滚动的是外层，内层 `scrollTop` 恒为 0 ⇒ 守卫失效 ⇒ **列表滚到中段后上滑仍会触发刷新**。

实测（`evidence/probe_pulltorefresh_in_sheet.py`，合成页面三臂）：

| 臂 | 接法 | 外层 `scrollTop` | 内层 `clientH`/`scrollH` | 内层 `scrollTop` | 守卫 |
|---|---|---|---|---|---|
| **A** | 朴素嵌套 | **1271**（外层在滚） | 1600 / 1600 ⇒ **滚不动** | **0（恒）** | **❌ 失效** |
| **B** | 根加 `height:100%` | 0 | 329 / 1600 | 1271 | ✅ |
| **C** | 对照：调用方持有滚动权 | —（无外层） | 361 / 1600 | 1239 | ✅ |

⇒ **朴素嵌套不可用**；B 能跑但**依赖外层 `py-4` + `flex-1` 恰好如此**（「碰巧对」而非「由构造对」）。
⇒ 建议给 `BottomSheet` 增加「把滚动权交给调用方」的开关（或让 `PullToRefresh` 接受外部滚动元素）。
**这是共享组件的 API 改动**，故 NR-11 需要定稿——见 §9 第 10 项。

#### ✅ 定稿（2026-09-26 · §9 第 10 项取 ①）：`scrollOwner` 开关

**已定稿并落地。** 草案与两轮实测存证：`deliverables/ui-design/design-draft-sheet-scroll-ownership-2026-09-26.md` ·
`evidence/sheet_scroll_contract_probe_2026-09-26.txt`。

**API**

```ts
scrollOwner?: "sheet" | "content";   // 默认 "sheet" = 现状逐字不变
```

| 模式 | 内容区渲染 | 谁在滚 |
|---|---|---|
| `"sheet"`（默认） | `scroll-thin min-h-0 flex-1 overflow-y-auto px-4 py-4` | `BottomSheet` 自己 |
| `"content"` | `flex min-h-0 flex-1 flex-col`（**不带内边距**） | 调用方 |

**为什么槽位是 `flex-col` 而不是 `grid`**（实测臂 F）：`grid-rows-1` 只支持**单**子元素 ——
塞 3 个子元素时**第一个被压成 0 高**（表头隐形）。而通知中心的内容天然是
「表头 / 滚动列表 / 页脚」**三段**（表头页脚要钉住）⇒ 必须 `flex-col`
（实测臂 S：表头 34px · 内层 293px · 页脚 34px，内层独占滚动）。

**调用方的两条义务**（实测臂 Q/R）：

1. 自己滚动的那一层要 `flex-1`（即 `<PullToRefresh className="flex-1">`）；
2. 若在槽位与滚动层之间**再包一层** `flex` 容器，那一层**必须带 `min-h-0`** ——
   否则调用方会被撑到内容高、内层**滚不动**（`scrollTop` 恒 0，**静默失效**，不报错）。

**为什么 `"content"` 不带内边距**：调用方既然接管了滚动，它**已经知道**自己的行/表头有没有内边距。
⚠️ 顺带修掉一处既有不一致：`BottomSheet` 槽位 `px-4` + `NotificationRow` 自带 `px-4`
⇒ 移动端通知行左右内边距曾是 **32px**，而桌面下拉面板是 **16px**。

> **本节的判据**：`evidence/verify_component_wiring.py`（`PullToRefresh` 由 `KNOWN_GAPS`
> 转为 `USED`）+ 真机渲染（内层 `scrollTop` 能否 > 0 ⇒ 守卫成立）。

##### 🚨 两个被实测挡住的落点（都不是「忘了做」）—— **一 已于 2026-09-26 解除**

**一、lawyer `/cases`：`PullToRefresh` 进不了「文档滚动」型页面。**

`PullToRefresh` 的手势守卫是 `el.scrollTop > 0 ⇒ 不接管`，读的是**它自己那个内层容器**
（`PullToRefresh.tsx:56/63`）。而律师端走 `AppShell`：`<div className="flex min-h-screen flex-col">`
+ `<main className="flex-1 …">` —— **页面由文档（`body`）滚动**，`main` 没有 `overflow`
⇒ 内层容器**永远不会滚**、`scrollTop` 恒 0 ⇒ 守卫失效（列表滚到中段仍会触发刷新）。
这正是本文件早先记过的**臂 A** 形态（合成实测：外层 `scrollTop=1271`、内层恒 0）。
im 之所以能接，是因为它**不是** `AppShell`。

⇒ **两条出路，都属共享包 / 规范改动 ⇒ 须拍板**：
① 让 `PullToRefresh` 支持**外部滚动元素**（`scrollTarget` 或传入 ref）—— 本文件早先就把它列为备选手段；
② 把 `AppShell` 的 `<main>` 改成滚动容器（`overflow-y-auto` + 定高）—— 影响四端**全部**页面，爆炸半径大。

#### ✅ 一 已解除（2026-09-26 · 拍板取 ①）：`PullToRefresh` 新增 `scrollTarget`

**API**

```ts
export type PullToRefreshScrollTarget = "window" | string | { readonly current: HTMLElement | null };
scrollTarget?: PullToRefreshScrollTarget;   // 不传 = 现状逐字不变
```

| 模式 | 内层容器的类 | 谁在滚 | 守卫读什么 |
|---|---|---|---|
| **不传**（默认） | `scroll-thin min-h-0 flex-1 overflow-y-auto overscroll-contain` | `PullToRefresh` 自己 | 内层 `scrollTop` |
| **传了** | `overflow-visible`（**不是**滚动容器） | 外部（文档 / 选择器 / ref） | 目标的 `scrollTop` |

**三条设计决定，各有实测依据**（`evidence/probe_ptr_scroll_target.py`，合成页三臂）：

1. **外部模式下必须去掉 `overflow-y-auto`** —— 留着它就还是「自己拥有滚动权」，既与外层形成双层滚动，
   又让内层 `scrollTop` 恒 0（守卫照样失效）。⚠️ **并且不能只看「内层滚不动」**：臂 A（没修）与臂 W（修了）
   的「滚不动」是**同一个测量结果、成因相反**（A 是拿到滚动权却无处可滚，W 是根本不持有滚动权）⇒
   判据必须查 `getComputedStyle(inner).overflowY`（`auto` vs `visible`）才分得开，
   否则会把「**没修**」读成「修好了」。实测：臂 A 文档滚 **788px** 而内层恒 **0**；臂 W 文档接管、
   内层 `visible`、内容未压扁（根高 / 内层高均 1600）。
2. **外部模式不带 `flex-1`** —— 该模式下根没有确定高度，`flex-basis:0%` 会退化成依赖
   「auto 高度容器里百分比基准按 content 解析」这条细节；不必要地押注它。
3. **取不到目标 ⇒ 返回 `null` ⇒ 不接管手势**（**不是**降级成 0）—— 0 会被当成「在顶部」⇒ **永远接管**，
   正是本参数要修的那个 bug。宁可不动，也不要错动。

⚠️ **本参数不解决**「原生 overscroll 与手势竞争」：外部模式下内层不再是滚动容器 ⇒
没有 `overscroll-contain` 可挂，浏览器自带的「下拉刷新 / 橡皮筋」在真机上仍可能抢先。
⇒ 属**真机渲染验证**范畴，走 `browser-all` job；**本文件不声称已解决**。

⚠️ **仍未解的是「二」**（im `/chat` 会话列表的 `InfiniteList`）—— 那是**先建一个功能**，不是接线。

> **本节判据**：`evidence/verify_component_wiring.py`（lawyer `/cases` 计入 ①产品，实测 **2 → 3**）·
> `evidence/probe_ptr_scroll_target.py`（三臂 + 七条源码级地板；⚠️ 地板**只挡回退、不能证真**）·
> 真机渲染（`browser-all`）。

现状：`GET /api/v1/conversations?page=1&page_size=50` —— **单页、无 `hasMore`、不显示总数**，
且列表按 **进行中 / 已结束** 分组（`groups`）；而 `InfiniteList` 的 `items` 是**扁平**模型。

## 6. 落地方案 C：§8.6 离线预缓存

### C.1 范围（照 §8.6 三项，不自行扩大）

1. 打开案件时预缓存 **六段式分析 + 证据索引 + 文书正文**，单案上限 **20 MB**
2. 缓存状态在**证据列表**用 **✓** 明示
3. 离线时顶部琥珀状态条 + 「重试」（**已实现**，不动）

### C.2 手段：**两层，别混为一谈**

| 层 | 解决什么 | 手段 | 不做会怎样 |
|---|---|---|---|
| **① 数据层** | **打开过的**案件离线可读 | 案件详情落 **IndexedDB**（按 `tenant_id + case_id` 分区） | 离线时案件列表在、点进去空白 |
| **② 外壳层** | **冷启动 / 刷新后 App 还能打开** | **service worker** 预缓存 App Shell（HTML + JS + CSS + 字体） | 律师**关掉 App 之后**进地下室再打开 = **白屏** |

> ⚠️ **只做 ① 不做 ② 是不够的。** §8.6 的场景是「律师在法院、看守所、地下停车场」——
> 律师**不会一直开着 App**。真实时序是「路上看了一眼 → 锁屏 → 进地下室 → 掏出手机打开」，
> 这一步是**冷启动**，只有 ② 能兜住。
> 反过来说：只做 ② 不做 ①，App 能打开但**案件内容是空的**，同样不满足「离线可读」。

⇒ **建议两层都做**，且**② 是 ① 生效的前提**（没有 ②，① 在冷启动路径上根本读不到）。

### C.3 20 MB 预算怎么算、怎么淘汰（**待拍板**，附推荐）

| 问题 | 推荐 | 理由 |
|---|---|---|
| 预算按什么计 | **按案件**，不是按端、不是按用户 | §8.6 原文就是「**单案**上限 20 MB」 |
| 超预算怎么办 | **LRU 淘汰**（保留最近打开的 N 个案件） | 律师的访问模式是**回到最近办的案**，LRU 与之一致 |
| 淘汰是否静默 | **不静默** | 设置页显示「已缓存 X 个案件 / Y MB」；否则「上周缓存的案今天打不开」会被当成 bug |
| 单案超 20 MB 怎么办 | **按优先级截断**：六段式分析 > 证据索引 > 文书正文 | §8.6 的列举顺序本身就是优先级 |
| 登出 | **清空**（按 `tenant_id + user_id` 分区，登出即清） | 与 NR-15 的缓存策略一致；当事人信息不能跨账号留存 |

### C.4 `✓` 明示放哪

§8.6 原文：「缓存状态在**证据列表**用 ✓ 明示」
⇒ 落在 `apps/lawyer/app/(app)/cases/[id]/page.tsx` 的 **`EvidenceTab`** 证据行上。

三态（建议）：

| 态 | 展示 |
|---|---|
| 已缓存 | `✓ 已缓存` |
| 缓存中 | `↓ 缓存中`（带进度或骨架） |
| 未缓存 | `— 未缓存`（**不是空白**——空白会被读成「已缓存」） |

### C.5 与待同步队列的关系（**别串线**）

| | 预缓存 | 同步队列 |
|---|---|---|
| 方向 | **读**（服务端 → 本地） | **写**（本地 → 服务端） |
| 冲突语义 | 以服务端为准（覆盖本地） | 以服务端为准，本地变更保留为批注草稿（§8.6） |
| 存储 | IndexedDB（分表） | IndexedDB（分表） |
| 登出 | 清 | 清 |

⇒ 两者**可以**共用 IndexedDB 实例，但**必须分表**；**共用一张表会把读缓存当成待补传的写操作发出去**。

### 7.6 `prefers-reduced-motion` 渲染级门禁 —— ✅ **已实现（2026-09-20）**

**为什么需要**：规范 §4.4（`§4.4「场景 · 时长 · 缓动」`）写「**必须**响应 `prefers-reduced-motion: reduce`」，
但此前**一条渲染级判据都没有**。而且它**不可能**被现有探针发现——

| # | 原因 |
|---|---|
| ① | 规范用了「必须」⇒ 有判据义务 |
| ② | 它是「**浏览器解析**出来的东西」：全仓 `prefers-reduced-motion` 命中 19 处，**18 处是产物副本**，源码里只有 `tokens.css:360` 一处 |
| ③ | 🚨 `cdp.py:284 freeze_animations()` **既**把媒体特性强制成 `reduce`，**又**注入无条件 `animation:none!important`。**测量手段覆盖了被测对象** ⇒ 凡调用它的探针都测不出真伪 |

⇒ 本门禁**不调用 `freeze_animations()`**，并把「出现 `style[data-cdp-freeze]`」做成**前提锁 ⇒ exit 2**。

**`evidence/verify_reduced_motion.py`**（**自检 24 臂**，退出码 `0/1/2`）：

| 判据 | 断言 | 出处 |
|---|---|---|
| **R2** | reduce 档下 `--dur-*` / `--pulse-iter` 运行时值 == `tokens.css` reduce 块声明值（**解析得到，不硬编码**） | 先证机制是好的 |
| **R1a** | reduce 档下不得有可见元素带非零 `transition-duration` | §4.4 + `tokens.css:358` 自述「全部过渡停下」 |
| **R1b** | reduce 档下不得有 **Tailwind 内置 `pulse`**（`2s infinite` 硬编码） | 装饰性骨架屏；项目内已有响应式对照 `animate-pulse-soft` |
| **R1d** | reduce 档下不得有**项目自定义动画**仍在跑 | 本该被 `--dur-*` 停下 |
| **R1c** | `spin` 加载指示仍在跑 ⇒ **只报不判**（⚠️ **2026-09-26 更新：#75 拍板后已升为判红**） | 承载「进行中」语义，属设计取舍 |

**两阶段采样**（这是本门禁的关键设计）：

| 阶段 | 手段 | 覆盖 |
|---|---|---|
| **稳态** | 正常加载 | 四端 × 2 页 × 2 视口 = 16 组 |
| **加载态** | `Fetch` 挂起 `*/api/*`，但**放行 `/auth/`** | 四端首页 × 2 视口 = 8 组 |

⚠️ **加载态那一段必须补**：spinner / 骨架屏**只在取数期间存在**，稳态下 DOM 里根本没有。

与 2 处 `animate-pulse`（2s 硬编码）一处都没被覆盖到**。⇒ 那片绿只覆盖了稳态那一小块。
（另：不能全挂 `*/api/*` —— **鉴权引导也是 `/api/`**，全挂会先卡在鉴权 spinner 上，到不了列表骨架屏。
「给网络加延迟」也不行：会把 **HTML 文档本身**拖慢，实测延迟 4s 时 1.2s 处只有 17 个 DOM 节点。）

**全量结果（24 组 / 2 组红）**：稳态 **16/16 通过**；加载态 6 通过、**2 红**（均为 im 首页骨架屏）；
R1c 4 处只报不判 ⇒ 已登记 §9 第 14 项与 #28。

2. **源码层**：**「统一」是一条关于「集合大小」的判据** —— 要收集全站焦点环的

3. **渲染层**：`:focus-visible` 是**伪类**，只有在**真的把它逼出来**之后才知道浏览器算出的
