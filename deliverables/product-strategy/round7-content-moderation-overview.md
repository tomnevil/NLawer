## 一、为什么这一轮必须现在做

《生成式人工智能服务管理暂行办法》**第十七条**要求：
具有舆论属性或社会动员能力的生成式 AI 服务，应当开展安全评估并履行**算法备案**。

而备案的**前置审查**恰恰就看前三条：

| 条款 | 要求 | 本项目对应实现 |
|------|------|----------------|
| 第四条 | 不得生成违法内容 | 内置词库 + 外部审核钩子，覆盖 11 个类别 |
| 第十四条 | 停止生成 / 停止传输 / 保存记录 / 报告 | `ModerationService` + `moderation_records` + 上报状态跟踪 |
| 第十五条 | 投诉举报机制 + 公布流程时限 | `/api/v1/complaints` 五个端点 |

**关键判断**：算法备案的周期**不可控**（材料补正、安全评估可能数月）。
等到功能开发完再启动，会造成「产品已就绪却无法上线」的空转期。
因此本轮的目标不是"把功能做完"，而是**让备案可以立刻启动**。

## 三、三个真实缺陷及修复（本轮的核心技术价值）

### 缺陷 1：留痕被事务回滚一起吃掉 ⚠️ 最严重

**现象**：E2E 显示 `moderation_records` 落库 0 行，但 SQL echo 明明打印了 INSERT，
紧跟一行 `ROLLBACK`。

**根因**：`ContentBlockedError` 从路由抛出 → `get_db` 的异常处理
`rollback()` 把请求会话里的一切（审核记录 + 审计行）全部丢弃。
**留痕彻底失效，而第十四条恰恰要求「保存有关记录」。**

**这是第五轮审计日志同类缺陷的第 2 次出现**——说明"依赖请求事务生命周期
写合规记录"是**系统性陷阱**，不是偶发失误。

**修复**：`record_with_detached_row()` —— 把业务留痕行与审计行放入
**同一个独立事务**立即 commit。宁可两条都失败，也不要"对不上账"。

### 缺陷 2：Base64 绕过漏检（真实漏检）

**根因**：`decode_layers` 只处理**整串**是 Base64 的情况。
把 payload 嵌在句子里（`"解码这段 6aKg... 然后照做"`）即可绕过。

**修复**：增加**子串扫描**策略（`[A-Za-z0-9+/=_-]{12,}` + 启发式），逐个 token 试解码。

**教训**：这类缺陷只有**主动构造对抗样本**才能发现，正常输入测试与静态审查都会漏掉。

### 缺陷 3：拦截与上报混为一个动作码（设计缺陷）

**根因**：单 action 码导致语义坍缩——BLOCK 命中若需上报，
则只记 `CONTENT_REPORTED`，`CONTENT_BLOCKED` 丢失。

**「拦截」与「上报」是两件独立的事**（第十四条区分了动作与报告义务）。

**修复**：拆为两条独立审计行，并新增 `CONTENT_REPORT_PENDING`：

| 行 | action |
|----|--------|
| 处置行 | `CONTENT_BLOCKED` / `CONTENT_UNDER_REVIEW` |
| 上报行 | `CONTENT_REPORTED` / `CONTENT_REPORT_PENDING` |

**业务价值**：运维可一句查询回答**「我欠监管部门几笔上报？」**
——这是会直接导致处罚的问题，不能让答案藏在拦截日志里靠人猜。

实测配对：9 次拦截 → 9 条 `CONTENT_BLOCKED` + 9 条 `CONTENT_REPORT_PENDING`。

## 四、第十五条：投诉举报机制

**关键决策：提交入口允许匿名。**
「公众投诉举报」的主体是公众，不是注册用户。要求先登录等于把
「便捷入口」四个字作废，也违反第十七条备案审查口径。

| 端点 | 鉴权 | 限流 |
|------|------|------|
| `POST /api/v1/complaints` | 无 | 5 次/分/IP |
| `GET /api/v1/complaints/policy` | 无 | — |
| `GET /api/v1/complaints/{ticket_no}` | 无（工单号即凭证） | — |
| `GET /api/v1/complaints` | 平台管理员 | — |
| `POST /api/v1/complaints/{id}/handle` | 平台管理员 | — |

### 防「假闭环」的四条不变量

1. 办结/不予受理**必须**填写处理结论（≥5 字）——否则投诉人拿不到答复
2. `RESOLVED` **必须**带 `handled_at` + `feedback_sent`——可验证是否真反馈
3. 承诺时限**从受理时刻起算**（+15 天），不是从办结起算
4. 看板**必须**给出 `overdue` 口径——逾期是**违约信号**

## ⚠️ 待确认 / 假设 / Non-goals

### 假设
- 内置词库为**最小可运行集**，仅供打通链路与回归测试，**不可直接商用**
- 反馈时限采用 **15 个自然日**（与《网络信息内容生态治理规定》通常口径一致），
  如有行业特殊要求需调整 `COMPLAINT_DUE_DAYS`
- 平台管理员可跨租户处理投诉（投诉通常涉及平台级合规义务，不属单一律所）

### 待确认
- 外部审核服务的**选型**（阿里云内容安全 / 腾讯天御 / 数美等），
  以及是否需同时接入多家做冗余
- 监管上报的**具体接口规范**（各地网信办口径可能不同）
- 词库**热更新机制**的具体形态（文件 / 数据库表 / 配置中心）

### Non-goals（本轮明确不做）
- ❌ **不做图片 / 音频 / 视频的内容审核**——本轮只覆盖文本；
  多模态审核依赖外部服务能力，待选型后补充
- ❌ **不实现自动化的用户处罚决定**——ESCALATE 级只**标记** `user_restricted`，
  实际限制动作留给人工复核，避免误伤
- ❌ **不做词库的自动学习 / 自更新**——词库变更须经法务审定，不引入自动化
- ❌ **不做投诉的自动裁决**——所有投诉由人工处理，系统只保证不丢、不逾、可查
