## 一、问题本质

审计的失效模式是**静默的**：漏掉一个端点不会报错，接口照样返回 200，
只有等合规检查或事故复盘时才发现「这个操作没留痕」。

修复前实测：全仓 `write_audit` **仅 2 个调用点**（注册、登录成功）。

| 无留痕的关键操作 | 性质 |
|------------------|------|
| 律师复核批准 / 驳回 / 归档 | 责任认定链断裂 |
| 开庭材料包导出 | 交付动作无法追溯 |
| 证据上传 / 解析 | 敏感卷宗流转无记录 |
| **卷宗原文下载** | 等保明确要求留痕 |
| 派单 / 接单 | 案件责任归属起点 |
| 文书生成 / 合同审查 | AI 产出责任归属 |

三个层次的问题：

1. **覆盖面缺失** —— 6 个文件完全空白
2. **上下文断链** —— `Request` 只在路由层，IP / UA / request_id 下不到 service 层
3. **事务生命周期错配** —— 登录失败（401 回滚）、文件下载（`FileResponse` 不走 commit）
   用主会话写审计会**随请求结束静默消失**

## 二、修复方案

### 双入口设计

| 入口 | 场景 | 事务语义 |
|------|------|----------|
| `record()` | 常规业务操作 | flush 到当前事务，随外层 commit |
| `log_detached_ctx()` | 主事务会回滚（登录失败）/ 响应不走事务（文件下载） | 独立会话，立即 commit |

### 关键实现

- **`app/core/audit_context.py`（新增）** —— `ContextVar` 存 IP / UA / request_id。
  **每请求隔离**（用全局 dict 会在并发请求间串 IP）；按列宽截断（IP 64 / UA 300 / rid 64），
  否则 Postgres `String(300)` 会直接 `IntegrityError`（SQLite 不校验，极易漏测）。
- **`record()` 自动补全** —— 调用方只传 `actor=user`，函数拆出 `actor_id` / `actor_role` /
  `tenant_id` 并补上下文；`role` 枚举自动取 `.value`；失败吞掉告警。
- **登录失败独立留痕** —— 区分 `BAD_CREDENTIALS` / `ACCOUNT_DISABLED`，
  且**用户名不存在时也留痕**（只记已存在账号等于给探测者留后门）。

### 覆盖的动作

`LOGIN_FAILED`、`KNOWLEDGE_CREATE/READ/DELETE`、`DISPATCH_CREATE/ACCEPT`、
`DOCUMENT_RENDER`、`CONTRACT_REVIEW`、`COMPLIANCE_SCAN`、
复核 7 项、归档 2 项、证据 2 项、分析 3 项、`FILE_DOWNLOAD`。

## ⚠️ E2E 抓到 3 个「静态检查全绿」的缺陷

**这是本轮最大的价值** —— 三个缺陷在编译与静态检查下**全部通过**：

1. **`LOGIN` 审计没有来源 IP / UA** —— `auth_service` 调的是**不读上下文的裸
   `write_audit()`**。静态检查只断言「出现了 `AuditAction.LOGIN`」就放过了。
   **对比证据**：同一文件里 `LOGIN_FAILED`（走 `log_detached_ctx`）有 `ip='testclient'`，
   而 `LOGIN` 是 `None` —— 只有真实请求链路能看出差异。
2. **`FILE_DOWNLOAD` 同样缺来源** —— 裸 `log_detached()`。由**新增的
   「禁止裸用上下文盲函数」守卫自动抓出**（断言立即报 `files.py:76`）。
   说明「把规则写成机器可验的断言」比「人肉 review」可靠。
3. **`success` 布尔恒等判断风险** —— SQLite 回读为 `int`，若业务写
   `if row.success is True:` 会**恒为假且不报错**。已加源码扫描用例钉死。

> **规律（第三次验证同一结论）**：第一轮 `Role` 导入缺失、第四轮 `JsonVector` 写入失败、
> 本轮上下文断链 —— 都是**静态检查抓不到、只有真实 DB / 真实 HTTP 才暴露**。
> 涉及持久化与请求链路的改动，必须有 E2E 层。
