## 二、核心判断：门禁必须"第一天就是绿的"

一条上线即红的 CI，**实际寿命只有两天**：第一天报红，第二天被注释掉，第三天没人记得它存在。

因此本轮的顺序是 **先清债 → 再上锁 → 本地模拟验证**：

```
步骤 1  让 ruff 全绿（清 52 个历史错误）
步骤 2  写 CI（ruff / compileall / pytest + 前端 tsc + docker build）
步骤 3  本地按 CI 原样跑一遍，确认 EXIT=0
```

### 52 个错误里，5 个是**真缺陷**而非风格问题

| 问题 | 判定 | 处理 |
|------|------|------|
| `app/database.py` 4× E402 | ✅ **真实缺陷** | 一行 `logger = ...` 被插在**导入块中间**，切断了导入语句 |
| `case_copilot.py` E741 | ✅ 真实可读性缺陷 | 变量 `l`（易与 `1` 混淆）→ `law` |

其余 47 个自动修复（未用导入 / 导入顺序 / 重复定义）。

**诊断脚本与根目录一次性脚本走 `extend-exclude` 排除，而非改代码**：
`verify_*.py` 必须在 `import app.*` **之前**设置 `DATABASE_URL`，E402 在此处是**设计使然**。

> **工程判断**：区分"代码写错了"与"规则在此场景不适用"是引入 lint 时最容易做错的决定。
> 前者必须修（否则规则形同虚设），后者必须显式排除并写明理由（否则开发者会开始习惯性 `noqa`）。

## 三、CI 门禁

三个 job，**全部无需外部服务边车容器**——直接受益于"零必需外部依赖即可完整启动"的设计。

| Job | 内容 | 三层递进 |
|-----|------|---------|
| `backend` | `ruff` → `compileall` → `pytest` | 风格 / 语法 / 行为 |
| `frontend` | `pnpm install --frozen-lockfile` → `pnpm typecheck` | **tsc 是唯一裁判** |
| `docker-build` | build-only（不推送） | 防"代码能跑但镜像构建不出来" |

**为什么前端必须跑 `tsc` 而非只跑 ESLint？**
第六轮批量改写 13 个页面鉴权守卫时，**静态 grep 完全看不出问题**，`tsc` 一次性报出 **11 个编译错误**。
类型检查能发现 grep 与 code review 结构性看不见的错误。

**安全细节**：`permissions: contents: read`（最小权限）、`concurrency: cancel-in-progress`（省额度）、失败上传诊断产物。

## 四、可观测性

新增 `app/core/metrics.py`（~150 行）+ `app/core/log_config.py`，**零新增运行期依赖**。

**为什么自建而不是引 `prometheus_client` / `structlog`？**
实际只用「计数器 + 直方图 + 文本导出」与「JSON sink + 上下文注入」四件小事，
自建完全可控；每多一个运行期依赖就多一份供应链风险。**与 CI 不需要边车容器是同一条原则。**

### 探针语义拆分（关键）

原来的单个 `/api/health` 是综合自检（含 LLM 档位配置），用它做容器探针会导致
**LLM Key 没配 → 探针失败 → 容器被反复重启**，而进程本身完全健康。

| 探针 | 检查内容 | 失败后果 |
|------|---------|---------|
| `/api/health/livez` | **只回答"进程还在吗"**，绝不碰 DB | 编排器**重启**容器 |
| `/api/health/readyz` | `SELECT 1` **真实 DB 往返** | 编排器**摘流量**，不重启 |

`readyz` 用 `SELECT 1` 而非连接池状态——连接可能被中间件/防火墙**静默断开**，只有真正往返才能发现。

**已同步修正 `docker-compose.yml`**：healthcheck 从 `/api/health` → `/api/health/readyz`。

## 五、⚠️ 本轮自己引入并修复的缺陷

### 缺陷 1：直方图桶不累计 → `histogram_quantile()` **静默**返回错误分位数

```
观测 5 / 50 / 500 / 5000，buckets = [10, 100, 1000]
错误实现 → [1, 1, 1, 4]   ← le=5000 竟然 ≤ le=500，违反单调性
正确实现 → [1, 2, 3, 4]   ← 累计
```

**为什么特别危险**：Prometheus 服务端**不会报错**，`histogram_quantile()` 只返回一个**错误的 P99**。
而 P99 是延迟告警的**唯一依据**——告警会在错误阈值上触发或不触发，且无人能察觉。

> **与第 8 轮是同一类错误的不同形态**：上轮是并发时"少计用量"（丢失更新），
> 本轮是分桶时"少计样本"（非累计）。**共同点：错误的结果不报错，只是数值不对。**
> 验证脚本 A.5 的"桶必须单调不减"断言当场抓住了它。

### 缺陷 2：Gauge 私有字段被外部直接读写

在途请求计数需要「读-改-写」，初版直接操作 `._values`——**任何字段重命名都会静默改坏计数逻辑**。
→ 补齐 `get()` / `inc()` / `dec()` 公开 API，`dec()` **夹到 0**（负值会污染面板且难以察觉）。

### 缺陷 3（同类）：限流指标用了原始路径

专门写了 `normalize_path()` 防基数爆炸，却在**唯一真正危险的那个调用点**绕过了它。
→ 已修正，并补端到端测试扫描所有 `path=` 标签断言无裸数字 ID。

## 六、配套告警规则（9 条 / 5 组）

原则：**每条都对应一个具体的用户可感知故障或合规风险**。
"看起来不太对"的告警会训练运维忽略告警，**比没有告警更危险**。

| 组 | 告警 | 阈值 |
|----|------|------|
| 可用性 | 5xx 率 > 5% / 实例不可达 | 5m / 2m |
| 延迟 | P99 > 5s | 10m |
| 安全 | 限流激增 / CSRF 拒绝激增 | >30 次/min |
| **合规** | **审计写入失败 > 0（零容忍）** | 任何 1 条 |
| 容量 | 队列积压 > 200 | 10m |

> **交叉验证**：已用脚本比对「告警引用的 8 个指标名」与「注册表导出的 12 个指标」，全部可解析。
> **指标名拼错的告警会永远不触发**——这是告警体系最阴险的失效模式。

## ⚠️ 待确认 / 假设 / Non-goals

**待确认**：
- 监控栈选型（自建 vs 托管）与告警通知落点（钉钉 / 飞书 / 邮件 / PagerDuty）
- `/metrics` 暴露范围：集群内 or 内网可达

**假设**：
- 生产部署形态支持 Prometheus 拉取（若为纯 Serverless，需改为 Pushgateway）
- 流量规模下进程内计数足够（多副本由 Prometheus 按 `instance` 聚合）

**Non-goals（本轮明确不做）**：
- ❌ 分布式追踪（OpenTelemetry）—— 当前 `request_id` 串接已满足单副本排障；跨副本调用链留待后续
- ❌ 指标持久化 —— 拉取模型下进程重启归零可接受；**本指标不应用于计费**（计费以数据库 `usage_records` 为准）
- ❌ 日志聚合后端（ELK/Loki）部署 —— 已产出 JSON 结构，接哪家由运维决定
- ❌ 全量覆盖率门禁 —— 覆盖率是好指标但坏目标，易诱导写无断言测试；先以"行为测试"为准
