## 1. 缺陷 A：额度扣减非原子

### 实测证据（修复前）

```
额度 limit=5，并发 20 请求 → used_count = 1 或 2
```

即 **18~19 个请求的用量从未被计入**，且其中大部分**没有转成工单**。原实现是"读额度 → 判断是否超限 → 自增"三步：

```python
q = await self.ensure_quota(...)      # 读
exceeded = q.exhausted                # 判
if not exceeded:
    q.used_count = (q.used_count or 0) + 1   # 写（基于旧快照）
```

并发时多个请求各自基于**同一旧值**计算，后写覆盖先写 —— 典型丢失更新（lost update）。

### 第二个缺陷：额度行重复

`ensure_quota` 的"查不到就插入"在并发首次使用时可能插入多行同一 `(tenant, type, period)`，把额度切成几份、**变相放大可用量**。

### 修复

1. **`consume_atomic()`**：用条件 UPDATE 把"判断 + 自增"合并为一条语句，由数据库原子求值：
   ```python
   update(UsageQuota).where(
       UsageQuota.id == quota_id,
       (UsageQuota.limit_count <= 0) | (UsageQuota.used_count < UsageQuota.limit_count),
   ).values(used_count=UsageQuota.used_count + 1)
   ```
   以 `CursorResult.rowcount`（1=扣减成功 / 0=额度已尽）判定结果，不再依赖应用层读取的快照。
2. **唯一索引** `uq_usage_quota_tenant_type_period`：把"额度唯一"约束下沉到数据库，应用层只能缓解、不能根治。
3. **`ensure_quota` 兜底**：捕获 `IntegrityError` → 回滚 → 重读，使并发首用安全。
4. **全部生产调用点迁移**：`qa.py`、`documents.py`（×2）、`billing.py` 已切到 `consume_atomic()`；`consume()` 保留但标注**已废弃**，仅用于前后对比验证。

### 修复后实测

```
额度 limit=5，并发 20 → used_count = 5，成功 = 5，工单 = 15   ✅ 零丢失、零漏单
并发建 15 个工单 → 工单号 15 个全部唯一（碰撞 0）             ✅
```

## 2. 缺陷 B：审计日志无保留期与归档

### 为什么这是缺陷（两个方向都是缺陷）

- **留存不足**：等保 2.0（三级）要求审计记录留存**不少于 6 个月**。原实现没有任何保留期管理，看似"永久保留"，实则无归档出口 —— 一旦磁盘压力上来只能手删，且删了没有凭证。
- **无限期留存同样是问题**：审计表无限膨胀拖垮查询，且 `detail` 字段可能含个人信息，与《个人信息保护法》最小必要原则冲突。

### 修复：三段式

```
保底留存（≥180 天） → 到期归档（gzip JSONL + sha256） → 归档校验通过后清理
```

| 组件 | 作用 |
|------|------|
| `AUDIT_RETENTION_DAYS = 365` | 默认保留 365 天（高于 180 天下限） |
| `retention_days()` | 配置低于 180 时**告警并强制抬到 180** —— 拒绝遵从错误配置 |
| `archive()` | 导出过期记录为 gzip JSONL，返回 `{path, rows, sha256}` 供核对；**只读不删** |
| `purge()` | **默认 dry-run**，必须 `confirm=True` 才删；分批删除；写 `AUDIT_RETENTION_PURGE` 墓碑 |
| `archive_then_purge()` | 推荐运维入口：归档行数 ≠ 待清理行数时**拒绝清理**（宁可保留，不可丢失） |

### 管理接口（仅平台管理员）

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | `/api/v1/audit/retention/stats` | 总量 / 过期量 / 最老最新时间 |
| POST | `/api/v1/audit/retention/archive` | 归档（只读） |
| POST | `/api/v1/audit/retention/purge` | 清理（默认 dry-run） |
| POST | `/api/v1/audit/retention/archive-then-purge` | 归档并清理（推荐） |
| GET | `/api/v1/audit/retention/policy` | **公开**：保留策略说明（合规审查直接取用） |

受 `AUDIT_RETENTION_ADMIN_ENABLED` 开关约束（生产可急停）；`/api/health` 暴露 `audit_retention` 块供巡检。

## 3. 过程中发现的第 3 次同类缺陷（机制性）

### 现象

清理审计日志时，"墓碑"审计写入失败：

```
ERROR | 审计写入失败（已重试 5 次，该条审计已丢失，请检查数据库锁竞争）:
(sqlite3.OperationalError) database is locked
INSERT INTO audit_logs (... 'AUDIT_RETENTION_PURGE' ...)
```

### 根因

`log_detached_ctx` 用的是**独立数据库连接**（这是它存在的意义：主事务回滚时仍能留痕）。若调用方此刻**仍持有未提交的写事务**，SQLite 会加库级写锁，独立连接写入直接失败；Postgres 也可能因行锁等待超时。

**这已是本项目第 3 次踩到同一坑**：
1. 第 5 轮：审计日志随请求事务回滚而丢失
2. 第 7 轮：内容拦截记录随 `ContentBlockedError` 回滚而丢失
3. 第 8 轮：清理墓碑被未提交的 DELETE 事务阻塞

### 根治（两处）

1. **`log_detached` 内置退避重试**（5 次，递增间隔），仍失败时打 **error** 级日志（原为 warning）——避免"看起来正常"。
2. **`purge()` 调整顺序**：先在主会话内提交删除，**再**写墓碑。顺序反了必踩锁。

> **工程约定（已写入代码注释）**：写审计前先问一句 —— "此刻是否还有未提交的写事务？" 若有，要么先提交，要么接受重试。
