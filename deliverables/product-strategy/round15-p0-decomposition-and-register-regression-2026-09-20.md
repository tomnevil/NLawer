## 3. P0-12 分解：把「整项阻塞」拆开后，可施工面从 0 变成 1/3

上一轮的判断是 `#12 无支付 SDK` —— 这是一句**整项**判断。拆到子项后，三项的阻塞性质完全不同：

| 子项 | 后端 | SDK | 前端 | 是否阻塞 | 依据 |
|---|---|---|---|---|---|
| **注册** | ✅ 已实现 | ❌ 无 `register()` | ❌ 无页、无入口 | **不阻塞** | `auth.py:67`；SDK 0 命中；`apps/*/app` 「注册」0 处 |
| **找回密码** | ❌ 无端点 | ❌ | ❌ | **半阻塞** | `auth.py` 只有 register/login/refresh/logout/me 五个路由 |
| **支付 / 充值** | ❌ 无通道 | ❌ | ❌ | **真阻塞** | `billing.py` 4 路由全是「用量」语义；`billing_service.py` 里 `充值` 只出现在**注释**里 |

⇒ **修正上一轮的表述**：不是「#12 被支付 SDK 阻塞」，而是「**#12 的支付子项被阻塞，注册子项是纯接线缺口**」。
这个区分决定了排期：注册可以**现在就做**，不必等支付。

### 3.1 一个「看起来像坑、其实是对的」的发现

`packages/ui/src/components/LoginShell.tsx:226` 有一句面向用户的文案：
`「未注册的手机号将自动创建账号」`。

按本项目纪律，这第一眼像「UI 承诺了不存在的能力」。实测后**撤回**这个怀疑：

- 该文案只在 `isPhoneMode` 下渲染；
- `LoginShell.tsx:34-40` 的注释明确写了：`"phone"` 模式「需要后端提供短信下发与验证码校验端点（当前 `app/api/v1/auth.py` 只有 register / login / refresh / logout / me），因此默认不启用——**与其展示一个点了没反应的入口，不如等接口就绪后再打开**」；
- 四端 `login/page.tsx` 传 `onPhoneLogin` / `onRequestCode` 的数量 **均为 0**。

⇒ 这是一处**诚实的、有意识的设计克制**，不是缺陷。**登记为「不要改动」，且写明理由**（与「漏掉的误差」区别开）。

⚠️ 顺带确认：该注释**本身就证实了**后端 `register` 端点存在——即「#12 无注册能力」的印象在组件层作者那里也不成立。

## 4. 本轮实做：为已修复的越权漏洞补上回归判据

### 4.1 缺口是怎么被发现的（不是从代码读出来的）

`app/schemas/auth.py:33` 的 `RegisterRequest` 文档字符串记录了：

> 早期版本曾暴露 `role` / `tenant_id` 字段并直接透传给 `AuthService`，
> **导致任何人可通过 `POST /auth/register` 自助注册为 `PLATFORM_ADMIN`**
> （再借 `X-Tenant-Id` 头跨租户读取全平台数据）。现统一由服务端固定为 CLIENT + 默认租户。

这是一个**已修复的高危越权**。但 `tests/` 下 `grep -ln "register"` 命中的两个文件
（`test_notification_push.py` / `test_observability.py`）**全是 WebSocket 连接管理器的
`ConnectionManager.register`**，与注册接口毫无关系。

⇒ 这正是本项目反复出现的那一族：**「关键词命中」≠「有判据」**（纪律 36）。
一个已修复的高危漏洞，**只要有人把 `role` 加回 schema，384 条回归会全绿**。

### 4.2 补的 10 条判据（两层防线各钉一条 + 一条攻击者路径）

新建 `backend/tests/test_auth_register.py`。修复本身是**两层纵深防御**，所以两层都要有判据——
只有一层时，改掉那一层就没人发现：

| # | 层 | 断言 |
|---|---|---|
| T1 | 入口 | `RegisterRequest` 不得声明 `role` / `tenant_id` |
| T2 | 入口 | body 硬塞的特权字段被**丢弃**、不被对象携带 |
| T3 | 服务 | `role` ∈ {PLATFORM_ADMIN, FIRM_ADMIN, LAWYER, ENTERPRISE_ADMIN} 直接调服务 ⇒ `PermissionDeniedError`，**且未落库** |
| T4 | 服务 | 默认落到 `CLIENT` + `settings.DEFAULT_TENANT_ID` |
| T5 | 服务 | 重名 ⇒ `ConflictError`，用户总数不增加 |
| T6 | 服务 | 口令散列存储（`hashed_password != 明文` 且 `verify_password` 通过） |
| T7 | **HTTP** | body 带 `role="PLATFORM_ADMIN"` 走完整 HTTP 链路 ⇒ 落库仍为 `CLIENT` |

**T7 是最要紧的一条**：前六条测的都是「组件」，T7 测的是「接口」。
两层校验之间还隔着依赖注入、中间件、序列化，**任何一环把 `role` 透传进去，前六条都会全绿而漏洞复活**。

⚠️ **T2 的判据形态要注意**：pydantic v2 默认是 `extra="ignore"`（不是 `forbid`），
所以「构造时不抛异常」是**正确行为**。断言必须写成「值没有被对象接管」（`not hasattr`），
写成「构造应抛异常」会得到一条**永不生效的假绿**。

### 4.3 故障注入：证明这些判据**会变红**

按本项目纪律 20/39，**全绿本身不算证据**——必须先证明判据具备检出能力。
做法是把历史漏洞**原样复现**三处（随后全部撤回）：

1. `RegisterRequest` 重新声明 `role` / `tenant_id`；
2. 端点改为 `role=Role(payload.role) if ... else Role.CLIENT` 并透传 `tenant_id`；
3. 服务层 `if role != Role.CLIENT:` 改为 `if False:`（摘除校验）。

| 状态 | 结果 |
|---|---|
| 正常态 | **10 passed** |
| 故障态 | **7 failed / 3 passed** |

- 转红的 7 条 = T1、T2、T3×4、T7 —— **全部安全相关判据**，含最关键的 T7；
- 保持绿的 3 条 = T4（默认值）、T5（重名）、T6（口令散列）—— **与越权无关，本就不该红**。

⇒ **检出能力与特异性同时被证明**：既不是「只会绿」，也不是「一改就全红」。

故障注入已**完全撤回**（`grep -rn "FAULT-INJECTION" app/` ⇒ 无命中，三处代码已核对回原文），
撤回后复跑 **10 passed**、`ruff` **All checks passed**。
