# 事故复盘：批量 PowerShell 窗口风暴导致系统内存耗尽崩溃

**日期**：2026-09-15
**类型**：事故复盘（Incident Postmortem）/ 工程环境安全
**参与成员**：方向明（主理人 · 产品舵手）——本次为工程环境事故，直接由主理人取证与收口，未编排产品工作流成员
**严重级别**：P0（开发机两次非正常关机，未保存工作丢失风险）

---

## 📌 TL;DR（执行摘要）

- **现象**：执行「清理临时验证目录」时，屏幕上瞬间弹出大量 PowerShell/控制台窗口，内存被占满，系统卡死并强制断电重启。
- **根因**：被删除的 `_tmp_verify/` 目录含 **49,478 个文件**（其中 42,717 个是 `node_modules`），而 WorkBuddy 沙箱对**每一次文件操作都新建一个客户端连接**；删除操作被逐个拦截并派发为独立控制台进程，形成**进程风暴 → 窗口风暴 → 内存耗尽**。
- **已确认两次崩溃**：9/14 约 17:26–17:56、9/15 约 07:15–07:37（事件 41 + 6008，**无内核转储 → 不是蓝屏，是内存耗尽硬卡死**）。
- **关键结论**：**这不是"内存不够"，而是"操作方式错了"**。30.87 GB 内存本身充足（当前仍被其他应用占 86.8%），真正的问题是「在 Agent 内对 5 万文件做递归删除」这一动作与沙箱的删除拦截机制产生了乘性放大。
- **下一步**：**禁止在 Agent 内做批量删除**；`_tmp_verify/` 交由用户在普通 Windows 终端手动清理；沉淀为硬规则。

## 1. 事故时间线（取证还原）

### 1.1 系统层证据：两次非正常关机

| 时间（本地） | 事件 ID | 来源 | 含义 |
|---|---|---|---|
| 2026-09-14 17:55:49 | **41** | Kernel-Power | 系统未正常关机即重新启动 |
| 2026-09-14 17:55:56 | **6008** | EventLog | 上次关闭（记录值 17:26:20）是意外的 |
| 2026-09-15 07:37:24 | **41** | Kernel-Power | 系统未正常关机即重新启动 |
| 2026-09-15 07:37:28 | **6008** | EventLog | 上次关闭（记录值 07:15:56）是意外的 |

**关键判据——有无内核转储**：

```
C:\Windows\MEMORY.DMP      2026/7/3 10:34:52   ← 陈旧，与本次无关
C:\Windows\Minidump\       （不存在）
```

> **结论：没有蓝屏转储。** 若是驱动/内核缺陷导致的 BSOD，Windows 必然生成 minidump。
> 没有转储 + 事件 41 = **系统彻底失去响应后被强制断电**，这是内存耗尽/严重颠簸（thrashing）的典型特征。

### 1.2 应用层证据：守护进程日志断档

对 `~/.workbuddy-ai/logs/daemon.log`（17,605 条记录）做时间断档扫描，**全日志仅有 2 处断档**，与两次关机完全对应：

| 断档 | 时长 | 断档前最后一条日志 |
|---|---|---|
| 09-14 17:55:35 → 17:59:25 | 3.8 分钟 | `[DaemonRPC] end #27896 wb:invoke elapsedMs=553 **SLOW**` |
| 09-15 07:37:01 → 07:38:14 | 1.2 分钟 | `enterprisePolicy:getMemberCustomModelPolicy OK 0.0ms` |

**崩溃前的降级信号**（第一次崩溃前 4 条全部标红）：

```
[17:55:35] [MethodCh] end #6790 wb:notifications:summary elapsedMs=552 SLOW
[17:55:35] [ConversationListPoller] poll done {"totalMs":563,"listMs":563}
[17:55:35] [MethodCh] end #6790 ... elapsedMs=552 SLOW
[17:55:35] [DaemonRPC] end #27896 wb:invoke elapsedMs=553 SLOW
```

> 一个"通知摘要"查询耗时 **552ms**、会话列表轮询 **563ms**——对一个本地进程而言这已经是**极端资源饥饿**的表现。
> 这正是内存颠簸死亡螺旋的可观测信号：CPU 时间几乎全被分页换入换出消耗，业务逻辑被拖慢到毫秒级变百毫秒级。

### 1.3 时间线疑点说明（诚实披露）

事件 6008 记录的最后正常时间为 **17:26:20 / 07:15:56**，而守护进程日志一直写到 **17:55:35 / 07:37:01**，两者相差约 29 / 22 分钟。

**最合理解释**：Windows 的"最后正常时间"标记是周期性写入的，在严重资源饥饿时该标记写入会长时间停滞。因此真实过程是：

```
内存耗尽开始（约 17:26）→ 系统进入卡死/极度缓慢状态约 29 分钟
  → 用户无法操作，强制断电（约 17:55）→ 重启 → 事件 41 写入（17:55:49）
```

**这 29 分钟的"假活"状态本身就是内存耗尽的旁证**——机器没有立刻死，而是长时间处于"能动但完全不可用"的状态。

## 2. 根因分析：四层放大链

### 第 1 层｜触发动作：在 Agent 内对 49,478 个文件做递归删除

对被删目录做文件数清点：

| 目录 | 文件数 | 说明 |
|---|---:|---|
| `fe_upgrade/` | 19,142 | 前端副本（含完整 `node_modules`） |
| `ov_test/` | 17,575 | 前端副本（含完整 `node_modules`） |
| `upgrade_venv/` | 5,999 | Python 虚拟环境 |
| `ov3/` | 5,657 | 依赖验证目录 |
| `upgrade_venv2/` | 894 | Python 虚拟环境 |
| 其余（`ov2/ov4/ov5/audit_archive/...`） | 211 | 杂项 |
| **合计** | **49,478** | **1.9 GB** |

其中 **42,717 个（86%）来自 `node_modules`**。

> ⚠️ **这是本次事故最应该被指责的一环**：`node_modules` 本不该出现在临时验证目录里。
> 前端依赖验证只需要 lockfile，**`pnpm install --lockfile-only` 即可完成验证**（这一点在第十一轮已经验证过），
> 把整个 `node_modules` 复制进临时目录，等于把一次"删几个文件"的操作变成了"删 5 万个文件"。

### 第 2 层｜放大机制：沙箱逐文件拦截

WorkBuddy 沙箱（`sandbox-core`，PID 2268）**对每一次文件操作都新建一个客户端连接**。证据来自 `sandbox_2268_020.log`：

```
[2026/9/14 17:55:35.637][19984][sandbox-core][I] accept_loop: 新客户端连接 client_id=242714
[2026/9/14 17:55:35.638][7588] [sandbox-core][I] io_loop: 新 client 连接 client_id=242714
[2026/9/14 17:55:35.638][7588] [sandbox-core][I] 处理命令: ModifyBackup (targetPath=...\reg11c.db-journal)
[2026/9/14 17:55:35.658][7588] [sandbox-core][I] io_loop: client 断开 client_id=242714
[2026/9/14 17:55:35.841][19984][sandbox-core][I] accept_loop: 新客户端连接 client_id=242715   ← +204ms
[2026/9/14 17:55:35.984][19984][sandbox-core][I] accept_loop: 新客户端连接 client_id=242716   ← +143ms
```

**`client_id` 每 143–204 毫秒递增一次**。按此速率：

```
49,478 文件 × 每文件至少 1 次连接（实际删除通常 2–3 次：检测/备份/删除）
≈ 50,000 – 150,000 次客户端连接 + 线程创建
```

沙箱日志本身也印证了删除类操作的存在：

| 日志文件 | delete | trash | Remove-Item |
|---|---:|---:|---:|
| `sandbox_2268_020.log` | 57 | 18 | 12 |
| `sandbox_center_37520_000.log` | 84 | 4 | 0 |

另外 `sandbox_2268_020.log` 大小为 **6.5 MB，而其 20 个同类日志均为约 10.5 MB**——说明该日志是**在写入过程中被硬生生截断的**，与崩溃时刻吻合。

### 第 3 层｜窗口风暴：每文件一个控制台进程

沙箱的删除拦截在 Windows 上需要派发**控制台宿主进程**。当这类进程以"未抑制窗口 + 未继承控制台"的方式创建时，Windows 会为每一个**分配新的控制台窗口**。

于是：

```
每删除 1 个文件 → 1 个控制台进程 → 1 个可见窗口 + 1 个 conhost.exe
```

**这就是用户看到的"跳出好多 PowerShell 窗口"的直接来源。** 不是 Agent 在开窗口，而是**删除拦截的每个进程都自带一个窗口**。

### 第 4 层｜内存耗尽：88 MB × 并发数 > 30 GB

实测单个 PowerShell 宿主内存占用：

```
powershell   数量=5   总内存MB=442.1   →  单进程 ≈ 88.4 MB
conhost      数量=16  总内存MB=131.6   →  单进程 ≈ 8.2 MB
```

按此计算并发上限：

| 并发进程数 | 内存需求 | 结果 |
|---:|---:|---|
| 100 | ≈ 8.8 GB | 危险 |
| 200 | ≈ 17.7 GB | 接近极限 |
| **350** | **≈ 30.9 GB** | **耗尽（机器总内存 30.87 GB）** |

而机器在事发时的可用内存本就极少：

```
总内存 30.87 GB   可用 4.06 GB   已用 86.8%     ← 当前实测（崩溃时更差）
```

**常驻内存大户**（当前实测，崩溃时同量级）：

| 进程 | 实例数 | 内存 |
|---|---:|---:|
| Tabbit Browser | 23 | 2,196 MB |
| DoubaoWork | 15 | 1,513 MB |
| CodeBuddy CN | 38 | 1,448 MB |
| Weixin | 5 | 657 MB |
| QQLive | 3 | 642 MB |
| msedgewebview2 | 37 | — |
| svchost | 82 | — |

**页文件配置**（非系统托管）：

```
c:\pagefile.sys   初始 10240 MB   上限 40960 MB
d:\pagefile.sys   初始 20480 MB   上限 40960 MB
AutomaticManagedPagefile = False
```

页文件峰值仅 786 MB / 774 MB——**远未用满**。这不是页文件配置错误，而是**进程创建速率超过了系统回收速率**：内存以"每秒数百 MB"的速度被瞬时占用，页文件扩容根本来不及跟上，系统直接卡死。

### 放大链总览

```
[1] 在 Agent 内递归删除 49,478 文件（42,717 个是 node_modules）
        ↓  ×50,000 次
[2] 沙箱逐文件拦截，每文件新建 IPC 连接 + 线程
        ↓  ×1 进程/文件
[3] 每个删除派发独立控制台进程 → 每个自带可见窗口
        ↓  ×88 MB/进程
[4] 数百并发 × 88 MB ≈ 30 GB → 内存耗尽
        ↓
[5] 分页死亡螺旋（业务调用 552ms SLOW）→ 系统硬卡死
        ↓
[6] 强制断电 → 事件 41 + 6008，无 minidump
```

## 3. 为什么会发生两次？（第二次崩溃的说明）

| 次序 | 时间 | 归因 | 置信度 |
|---|---|---|---|
| 第 1 次 | 09-14 约 17:26–17:56 | **明确归因**：删除 `_tmp_verify/` 的窗口风暴 | 高 |
| 第 2 次 | 09-15 约 07:15–07:37 | **待确认**：崩溃前日志无异常（末条 `OK 0.0ms`），疑似开机后残留状态触发 | 中 |

第二次崩溃前的日志完全正常（最后一条是 `getMemberCustomModelPolicy OK 0.0ms`，无 SLOW 告警），无法从日志直接归因。**可能的诱因**（按可能性排序）：

1. **开机后对残留 5 万文件的扫描**：Windows Defender 实时防护、Search Indexer、以及 WorkBuddy 的文件监听器在启动时遍历 `_tmp_verify/`（1.9 GB / 49,478 文件），叠加开机高峰内存占用；
2. **上一次被中断的删除操作被重试**；
3. 与本次事故无关的其他环境因素。

> **行动要求**：第 2 次崩溃需在清理 `_tmp_verify/` 后观察 48 小时确认不再复现。

## 4. 排查思路（Playbook：下次遇到同类问题的标准动作）

### Step 1｜判断是不是"崩溃"以及崩溃类型

```powershell
# 近 8 天崩溃类事件（41=非正常关机, 6008=意外关闭, 1001=蓝屏, 2004=资源耗尽）
Get-WinEvent -FilterHashtable @{LogName='System';Id=@(41,6008,1001,2004,2005);
  StartTime=(Get-Date).AddDays(-8)} |
  Sort-Object TimeCreated |
  Select-Object TimeCreated,Id,ProviderName,@{n='Msg';e={($_.Message -split "`r?`n")[0]}} |
  Format-Table -AutoSize -Wrap
```

### Step 2｜区分"蓝屏"与"硬卡死"

```powershell
Get-ChildItem 'C:\Windows\MEMORY.DMP' -Force | Select-Object LastWriteTime,Length
Get-ChildItem 'C:\Windows\Minidump' -Force
```

- **有转储** → 内核级缺陷（驱动/内存），查转储；
- **无转储 + 事件 41** → **内存耗尽 / 硬卡死 / 强制断电**，走 Step 3。

### Step 3｜用日志断档定位崩溃精确时刻

对任意 JSONL 日志做时间断档扫描（阈值 60s）：

```python
import re, datetime
lines = []
for line in open(r"<日志路径>", encoding="utf-8", errors="replace"):
    m = re.search(r'"timestamp":"([^"]+)"', line)
    if m:
        lines.append(datetime.datetime.fromisoformat(m.group(1).replace("Z", "+00:00")))
for a, b in zip(lines, lines[1:]):
    if (b - a).total_seconds() > 60:
        print(f"断档 {(b-a).total_seconds()/60:.1f} 分钟: {a} -> {b}")
```

**这是定位崩溃点最可靠的手段**——比事件日志的"最后正常时间"准确得多。

### Step 4｜识别"进程风暴"

```powershell
Get-Process | Group-Object ProcessName | Sort-Object Count -Descending |
  Select-Object -First 20 @{n='数量';e={$_.Count}},@{n='进程名';e={$_.Name}} |
  Format-Table -AutoSize
```

**判读**：若 `powershell` / `conhost` / `cmd` 数量异常（正常应 <20），即为进程风暴。

### Step 5｜检查沙箱拦截日志

```bash
tail -50 ~/.workbuddy-ai/logs/sandbox/*/sandbox_*.log
grep -ci 'delete\|trash\|Remove-Item' ~/.workbuddy-ai/logs/sandbox/*/sandbox_*.log
```

**判读**：`client_id` 快速递增 = 逐文件拦截正在发生，**立即中止当前操作**。

### Step 6｜评估内存余量（操作前必做）

```powershell
$os = Get-CimInstance Win32_OperatingSystem
"可用 {0} GB / 共 {1} GB，已用 {2}%" -f `
  [math]::Round($os.FreePhysicalMemory/1MB,1),
  [math]::Round($os.TotalVisibleMemorySize/1MB,1),
  [math]::Round(100-($os.FreePhysicalMemory/$os.TotalVisibleMemorySize*100),1)
```

**硬性阈值**：**可用内存 < 8 GB 时，禁止任何批量文件操作。**

## 5. 避免复发的建议（按优先级）

### 🔴 P0 — 立即可做的硬规则

| # | 规则 | 具体做法 |
|---|---|---|
| 1 | **禁止在 Agent 内做批量删除** | 任何涉及 >500 文件、或路径含 `node_modules` / `site-packages` / `.venv` 的删除，**一律交由用户在普通 Windows 终端手动执行** |
| 2 | **临时目录不落地 `node_modules`** | 前端依赖验证一律用 `pnpm install --lockfile-only`（只需 lockfile 即可验证），**禁止完整 install 到临时目录** |
| 3 | **临时目录使用后立即改名为 `.deleting-<日期>` 并留待手动清理** | 重命名是单次系统调用（同卷内近乎瞬时），**不触发逐文件拦截** |
| 4 | **删除前先查内存** | 可用 < 8 GB → 拒绝操作，先关闭后台应用 |

### 🟠 P1 — 环境加固

| # | 措施 | 说明 |
|---|---|---|
| 5 | **关闭常驻大户再做大操作** | 当前 Tabbit(2.2GB)、Doubao(1.5GB)、CodeBuddy(38 进程)、msedgewebview2(37 进程)、微信、QQLive、飞书 等合计占用超 10 GB |
| 6 | **页文件改为系统托管或提高初始值** | 当前 `AutomaticManagedPagefile=False`，C: 初始 10 GB / D: 初始 20 GB。建议改为系统管理，让扩容更平滑 |
| 7 | **建立"删除批处理"纪律** | 确需在 Agent 内删除时，**每批 ≤ 500 文件**，每批后校验内存与进程数，异常立即停止 |
| 8 | **优先"移动/重命名"而非"删除"** | 跨卷移动会退化为复制+删除，**同卷移动才是瞬时操作**，注意区分 |

### 🟢 P2 — 长期改进

| # | 措施 | 说明 |
|---|---|---|
| 9 | **为沙箱删除拦截增加批量模式** | 建议向 WorkBuddy 反馈：批量删除应支持"单次连接处理 N 个文件"，避免逐文件新建 IPC 连接与控制台进程 |
| 10 | **临时目录加内存/文件数守卫** | 在验证脚本中内置守卫：若目标目录文件数 > 5,000，拒绝在 Agent 内删除并提示手动处理 |
| 11 | **开发机定期重启释放碎片** | 本次事故后系统已重启 2 次，内存压力已缓解；建议每日开工前重启一次 |

## 6. 本次事故的遗留项与后续动作

### 6.1 清理执行结果（✅ 已完成，2026-09-15 21:29）

**第一步：用户在普通 Windows 终端执行原生 `rd` 命令**（绕开 Agent 拦截层）

| 目标 | 结果 |
|---|---|
| `backend/_tmp_tests/` | ✅ 一次性删除成功，零错误 |
| `backend/_tmp_verify/` | ✅ **49,478 个文件 → 4 个**，仅剩 4 个被占用的日志文件 |
| 过程中是否崩溃 | ✅ **未崩溃**，无窗口风暴 |

> **关键验证**：同样的删除动作，**在普通终端执行时完全正常**——这反向证实了根因判断（问题不在"删除"本身，而在"经由 Agent 拦截层逐文件派发"）。

**第二步：定位并停止占用文件的残留服务**

4 个文件删除失败的原因是被运行中的进程持有。定位结果：

| PID | 进程 | 端口 | 内存 | 身份 | 启动时间 |
|---:|---|---|---:|---|---|
| 33740 | `python.exe` | 8001 | 113 MB | NLawer 后端（每分钟执行任务队列心跳回收） | 09-15 11:57 |
